# Recommended practice for an agentic design system

Scope: what practitioners and vendors say an agentic design system should be, and how an organization should adopt one, as of 21 November 2026. Recommendations below are tied to a source. Conference claims about Indeed, GitHub Primer, Spotify Encore, and Brad Frost’s “progressive disclosure” framework are reported by Into Design Systems; the talk recordings were not independently reviewed for these notes. Where a page states no publication date, that is said explicitly.

A working definition used by more than one source: an agentic design system is infrastructure an agent can read, apply, and be checked against. Tokens, component contracts, and usage rules are machine-readable. The distinguishing claim is not that an agent can generate UI, but that something outside the model can say the output is wrong. [Into Design Systems, “Agentic Design Systems: The Complete Guide,” AI Design Systems Conference 2026](https://www.intodesignsystems.com/agentic-design-systems); [Aestheria, “What is an agentic design system?,” field status dated in the post as August 2026](https://aestheria.design/blog/what-is-an-agentic-design-system).

## What sequenced adoption paths and maturity models do credible sources recommend?

### Takeaway

Credible sources agree that agents should sit on top of an already explicit system: naming, semantic tokens, component contracts, and documentation an agent can retrieve. They do not agree on the first week of work. Conference speakers and an eight-pillar readiness model start with foundations if those are weak. Supernova’s October 2026 study of 31 public systems says tokens and typed APIs are already mostly done, so the next work is a consumer `AGENTS.md`, `llms.txt`, and a read-only MCP server.

### Cited Findings

#### What sources say teams should do

- Romina Kavcic’s sequence, as reported from the AI Design Systems Conference 2026: “Plant seeds, not trees.” Start with naming conventions, token structure, and component descriptions. Do not chase full autonomy on day one. The same report says Brad Frost told the conference this applies at every design-system maturity level, and that even a JSON schema per component (identity, props, variants, sizes, states, usage) beats no context. [Into Design Systems, “Agentic Design Systems: The Complete Guide,” 2026 conference; page has no separate publication date](https://www.intodesignsystems.com/agentic-design-systems); restated by [Sil Bormüller, “Your Design System Is Not Ready for AI Agents,” Into Design Systems, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- The same conference synthesis publishes a seven-step start, attributed speaker by speaker: (1) foundations before automation, Romina Kavcic; (2) a JSON schema per component rather than prose, Diana Wolosin, Indeed; (3) Figma descriptions that state intent and composition, not only specs, Romina Kavcic; (4) trust levels per action (auto-merge, draft a PR, or suggest only), Romina Kavcic; (5) colocate rules and use semantic names such as `danger.background` rather than `red-500`, plus parseable front-matter, Jan Six, GitHub; (6) benchmark JSON vs Markdown vs hybrid on real queries before committing to an MCP format, Diana Wolosin; (7) pair-program with a developer, not a weekly sync, Romina Kavcic. [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems).
- Context delivery order from that guide, attributed across Romina Kavcic and Brad Frost: always-on rules for foundations (spacing, color, typography); MCP on demand for components; `AGENTS.md` as the orchestration file that points at the MCP server and sets trust levels. The stated reason: MCP returns only what the prompt asks for, so a “build a card” prompt will not pull spacing and type, and the model fills those gaps. [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems); [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents). Brad Frost’s own 16 December 2025 post does not describe this three-layer file scheme. It says Design Systems + AI should constrain generation to “high-quality design system materials,” as distinct from vibe coding, and points to Storybook’s MCP as a way to generate UI from a component library. [Brad Frost, “Agentic Design Systems in 2026,” 16 December 2025](https://bradfrost.com/blog/post/agentic-design-systems-in-2026/).
- Diana Wolosin’s format rule, as reported: JSON for MCP (component APIs, props, sizes, variants are a contract); Markdown for instructions to the model. Her benchmark, as reported: 77 components parsed from MDX, 8 MCP configurations, 1,056 prompts. Markdown used about 30,000 tokens per query, 82% coverage, with hallucinations. JSON had higher accuracy, about 80% fewer tokens, and about 5× lower annual cost ($300 vs $1,500). [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents); [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems).
- Before connecting an MCP, Sil Bormüller’s write-up of Romina Kavcic says to validate meaning across layers: token name, component description, and documentation of the current API must agree. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- Matthew Huntsberry publishes an eight-pillar AI Design Infrastructure Readiness Model. Each pillar is scored 1–5: 1 Fragmented, 2 Emerging, 3 Documented, 4 Governed, 5 Automation-ready. Pillars, in his order: (1) token taxonomy, (2) Figma library architecture, (3) component API alignment, (4) typography and responsive behavior, (5) design and code parity, (6) documentation system, (7) accessibility and governance, (8) AI / MCP readiness. He states that every other pillar is necessary and that pillar 8 is only the integration layer. “What good looks like” for tokens is a three-tier taxonomy (primitive / semantic / component), names that describe meaning (`color-text-secondary`) rather than appearance (`gray-400`), one source of truth, and an owner per token. Automation-ready means patterns are machine-readable contracts and the system can endorse the AI output. The page does not give a publication date. [Matthew Huntsberry, “The AI Design Infrastructure Readiness Model”](https://www.mmhuntsberry.com/methodology).
- zeroheight’s maturity book uses six axes, adding AI Readiness to an older Sparkbox-style model: Foundations, Documentation & Knowledge, Governance & Team, Adoption, Measurement & Impact, and AI Readiness. Each axis has four stages and behavioral signals. The marketing page does not list the stage names or the AI-readiness behaviors. Foreword by Ben Callahan. The page does not state a publication date; its hero image URL contains `/2026/08/`, which is a CMS path, not a stated date. [zeroheight, “Measuring Design System Maturity”](https://zeroheight.com/resource/measuring-design-system-maturity/).
- Designesy publishes a scored “AI Readiness contract” and says AI readiness is zeroheight’s 6th maturity axis (zeroheight 2026). Its page lists ten checks: machine-readable DTCG/JSON tokens, `llms.txt`, `/.well-known/agent.json`, an MCP `tools/list` endpoint, `DESIGN.md`, token `$description` fields, a machine-readable component schema, `sitemap.xml`, a permissive `robots.txt`, and Open Graph plus Twitter meta. Score = (points / 10) × 100 with PASS = 1 and WARN = 0.5. The page does not state a publication date. The last three checks are crawl and social-meta checks, not design-system practice argued by the conference speakers. [Designesy, “AI Readiness contract”](https://www.designesy.org/contracts/readiness).
- Supernova’s practical path is ordered by effort, smallest job first, and is explicitly for systems that already publish tokens and typed APIs. Step 1, an afternoon: an `AGENTS.md` for consuming teams (import paths, token naming, “hardcoded values are never acceptable,” the ten mistakes agents make, deprecations and replacements, where the MCP or `llms.txt` lives), shipped inside the package, plus one line in getting-started docs telling product repos to read that file. Step 2, a day or two: `llms.txt`, ideally `llms-full.txt` or markdown for every docs page. Step 3, a few days if missing: tokens as JSON or JS, Style Dictionary and/or DTCG; Carbon’s themes are cited as DTCG JSON. Step 4: component APIs as TypeScript types, a `custom-elements.json` manifest, or per-component option files (GOV.UK `macro-options.json` is the example). Step 5, the largest job: a read-only MCP exposing tokens with resolved values per theme, component APIs and usage rules, doc search, and deprecations with replacements. Primer’s and PatternFly’s servers are cited as open-source references. Supernova says the first two steps are about a week for most systems. The Part 2 page does not state its own publication date; it is the sequel to the study checked 5–6 October 2026. [Supernova, “AI-Ready Design Systems, Part 2: How to Make Your Design System Fully AI-Ready”; author not named on the page](https://www.supernova.io/blog/how-to-make-your-design-system-ai-ready).
- An earlier Supernova roadmap (page date not stated) lists, without a strict sequence: metadata and semantics, API or MCP exposure, design/code alignment, documentation with rationale and constraints, context scoped per consumer rather than the whole system, linting and anomaly detection, governance (versioning, access, update workflows), and team education. It says an agent handed the entire system performs worse than one handed the relevant slice. [Supernova, “AI-Ready Design Systems: Preparing Your Design System for Machine-Powered Product Development”; author and date not stated on the fetched page](https://www.supernova.io/blog/ai-ready-design-systems-preparing-your-design-system-for-machine-powered-product-development).
- Josef Richter’s pipeline, with a “state of the art” dated July 2026 in the post: keep W3C DTCG JSON canonical; compile with Style Dictionary; expose intent metadata over MCP; map back to the canvas with Code Connect. He says DTCG’s first stable module was v2025.10 on 28 October 2025 (he names Adobe, Google, Meta, and Figma among backers). He says the three-tier primitive → semantic → component model, with a `$description` on each token, is now consensus, and that the common failure is authoring primitives and describing semantics in prose instead of encoding a semantic tier the compiler can follow. He places `DESIGN.md` (Google Labs, which he dates to April 2026) downstream of DTCG as the agent-facing layer: YAML tokens plus Markdown rationale, alongside `AGENTS.md` and `SKILL.md`. He says reviewers still call `DESIGN.md` pre-1.0 and “not yet a safe production dependency.” These DTCG and DESIGN.md facts are Richter’s; the DTCG site and the DESIGN.md README were not independently verified here. A fetch of `github.com/google-labs-code/design.md` returned almost no specification text. [Josef Richter, “Building an Agentic Design System,” state-of-the-art section dated July 2026 in the post; a separate byline date was not in the extracted text](https://josefrichter.design/blog/agentic-design-system).
- Aestheria, writing in August 2026, rejects a ladder (traditional → computational → generative → agentic) and describes a dependency stack: assets, then logic (rules and constraints), then generation, then agency. “An agent without the logic layer beneath it is not a more advanced design system.” Three things to do before agents are urgent: write rules so a failed check is possible; name the external standard generated UI is tested against; decide inspect, override, and roll back before agents write production UI. [Aestheria, August 2026](https://aestheria.design/blog/what-is-an-agentic-design-system).
- Brad Frost, TJ Pitre, and Ian Frost’s course curriculum (announced 24 November 2025; course site fetched later and undated as a page) is a teaching sequence, not a maturity model: core concepts, tool and MCP setup, use AI to audit and synchronize the design system, then use both to build products. The November 2025 post names TJ Pitre of Southleft. The course site fetched in this research names him Product Architect for AI & Design Systems at Figma. Those two attributions were not reconciled. [Brad Frost, 24 November 2025](https://bradfrost.com/blog/post/introducing-our-new-course-ai-and-design-systems/); [AI & Design Systems course site](https://aianddesign.systems/).
- Figma’s current MCP docs say the remote server at `https://mcp.figma.com/mcp` is the recommended connection, and that skills should cover Code Connect, generating design-system rules from the codebase, translating designs to code, and reading Figma Specs. The help center says the server is not a one-click path from design to finished code: the agent knows system conventions only if they are shared through Code Connect, variables, rules, or prompts. [Figma, “Introduction” to the MCP server, developer docs; no publication date on the page](https://developers.figma.com/docs/figma-mcp-server/); [Figma Help Center, “Figma MCP server FAQs”; no publication date](https://help.figma.com/hc/en-us/articles/39252411778583-Figma-MCP-server-FAQs).

#### What sources say teams do today, where the source contrasts it with the recommendation

- Supernova scored 31 public design systems on 5–6 October 2026, five checks, two points each. Tokens as installable JSON or JS: 28 of 31 at full marks (the table shows 2 points for tokens on most rows). Typed component APIs: 26 of 31 at 2 points. Official MCP servers maintained by the system team are a small minority (the prose says 9 official MCP servers). Docs an agent can read in full: 3. Agent guidance for consuming teams: 3. Median score 5 out of 10. Nobody scored 10. Of 148 missing points, 135 sit in agent access, docs, and guidance; tokens and APIs account for 13. Twelve systems have an `AGENTS.md`, and all twelve are written for contributors to the design-system repo, not for engineers consuming the system in product repos. Supernova’s contrast: teams assume the remaining work is restructuring tokens and APIs; for these 31, that work is largely finished, and two static files (consumer guidance and an `llms.txt`) would move the median from 5 to 7 and the top band from 9 systems to 26. [Supernova, “How AI-Ready Are Design Systems? We Scored 31 in 2026,” checked 5–6 October 2026; author not named](https://www.supernova.io/blog/ai-ready-design-systems-2026-study).
- The same study: Primer’s MCP was the oldest dated official or pre-release server they could date, first published August 2025. Helios published a first version on 21 September 2026. GOV.UK Design System, U.S. Web Design System, and Fluent UI had MCP servers built by people outside the owning team. Five government systems averaged 3.2 out of 10; the other 26 averaged 5.6. Porsche Design System, DB UX, and Carbon by Sage ship consumer guidance inside npm packages, but Porsche’s and DB UX’s package READMEs do not mention those files, so an agent in a product repo will not see them. [Supernova, 5–6 October 2026](https://www.supernova.io/blog/ai-ready-design-systems-2026-study).
- This contrasts with the conference sequence. Supernova tells public-system owners to start with consumer `AGENTS.md` and `llms.txt` because tokens and APIs already exist. Into Design Systems, Huntsberry, and Richter tell teams whose foundations are weak to encode naming, semantic tokens, and contracts before agent access. Both can be true for different starting points; neither source says the other is wrong. [Supernova Part 2](https://www.supernova.io/blog/how-to-make-your-design-system-ai-ready); [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems); [Huntsberry](https://www.mmhuntsberry.com/methodology); [Richter, July 2026 state of the art](https://josefrichter.design/blog/agentic-design-system).

### Inferences

- A roadmap can treat “foundations first” and “tell agents where the data is” as two gates, not one checklist. Gate A is Huntsberry’s pillars 1–7 and the conference “seeds.” Gate B is Supernova’s five checks. Skipping Gate A matches the failure modes in the next sections. Skipping Gate B matches the October 2026 public-system scores.
- Supernova’s “smallest job first” order is a recommendation only for systems that already score 2 on tokens and APIs. Applying it to a flat, unnamed, or prose-only system would invert the conference advice.

### Gaps

- No published maturity model was found that numbers phases exactly as “tokens, then naming, then component APIs, then documentation, then agent rules, then evals.” The pieces exist across Huntsberry, Supernova, and the conference steps, but not as that single checklist.
- zeroheight’s four stages per axis, including the behavioral signals for AI Readiness, are inside the book. They are not on the public marketing page, so they are not quoted here.
- Huntsberry, Supernova Part 2, the Supernova “preparing” article, Designesy, and the Figma doc pages do not state publication dates.
- Schema by Figma and Clarity conference talks from 2024–2026 were not retrieved as primary transcripts in this pass.
- Richter’s DTCG date and the DESIGN.md April 2026 release were not confirmed on the W3C or Google Labs primary pages.

## What governance do sources recommend?

### Takeaway

Sources recommend a human owner, a contribution path that includes agent-made changes, and permissions copied from the human who invoked the agent. They split on how far an agent may go: GitHub Primer, as reported, limits agents to opening issues; zeroheight’s October 2026 MCP-Write creates drafts by default but also allows an agent to merge; Romina Kavcic’s reported model allows auto-merge only for low-risk, high-confidence edits.

### Cited Findings

#### What sources say teams should do

- Huntsberry: every token has an owner. Figma publishing is gated by a small group with review responsibility. Variant axes map one-to-one to engineering props. Deprecation moves through Figma and code in the same release. Contribution paths, review checks, and architectural decision records (why, not only what) are part of “what good looks like.” Accessibility is encoded in the component and tested in CI, not left for product teams to add later. The contribution process has to “scale to AI-assisted contributions,” or those contributions bypass review. The page has no publication date. [Matthew Huntsberry](https://www.mmhuntsberry.com/methodology).
- Romina Kavcic, as reported: trust is per action, not per agent, compared to career levels. Intern = suggest only. Junior = mechanical fixes. Some decisions “will never go past level three” because they always need human judgment. Sil Bormüller’s restatement of the levels: auto-merge for high confidence and low risk (lint fixes, documentation typos, accessibility labels); draft PR for medium confidence (token value updates, component description changes); suggest only for low confidence or high impact (new component APIs, breaking changes, governance decisions). [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems); [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- Jan Six, GitHub Primer, as reported by the same posts: agentic daily QA and maintenance use “safe outputs.” An agent can only create an issue, never merge code. Workflow described: start in Storybook, push to a preview environment, invite review. An accessibility-reviewer sub-agent is used so the main context stays small. Primer also has a public MCP and instruction files. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents); [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems).
- zeroheight governance product page: unfinished work stays separate from published guidance; page and component statuses; versioned releases; roles for who can view, contribute, and manage; control of which guidance agents can access. The page defines governance as ownership, rules, and workflows for who can contribute, how changes are reviewed and published, and how outdated guidance is retired. It does not spell out a deprecation mechanic beyond that definition. No publication date on the page. [zeroheight, “Design Systems Governance”](https://zeroheight.com/features/governance/).
- zeroheight MCP-Write, Seb Sidbury, 15 October 2026: write access mirrors existing permissions. Only admins and editors can write; if you can do it in the app, you can do it via MCP. New pages and edits are drafts first, so nothing is published before a person can review. Sidbury also says merging can happen via MCP-Write, so bulk jobs that should not wait for a manual review are not blocked. He says to test on a subset before asking the agent to merge in bulk. Out of scope as of that post: creating styleguides, changing settings, managing tokens, creating releases, and adding Figma or Storybook files. The recommended start is one workflow, then review the draft and merge when it meets the bar. Viewers can be given read-only MCP via SSO or a link; login is the preferred connection for read and write. [Seb Sidbury, “MCP-Write: What changes when AI can write to your design system?,” zeroheight, 15 October 2026](https://zeroheight.com/blog/mcp-write-what-changes-when-ai-can-write-to-your-design-system/); [zeroheight, “zeroheight MCP”](https://zeroheight.com/mcp/).
- Supernova: start the design-system MCP read-only. Minimum surface includes deprecations and their replacements. Consumer `AGENTS.md` should say what is deprecated and what replaces it, and which packages not to import. Access control, adoption data, and governance are three enterprise criteria Supernova says cannot be scored from outside an organization; their Claude skill asks about them separately. [Supernova Part 2](https://www.supernova.io/blog/how-to-make-your-design-system-ai-ready); [Supernova study, 5–6 October 2026](https://www.supernova.io/blog/ai-ready-design-systems-2026-study).
- Nathan Curtis, on the Wireframe podcast published 28 October 2026: version the spec. A command diffs a Figma branch against the current spec and emits a table of breaking, minor, and patch changes across components, examples, and content, as part of cutting a release. He wants the spec unbiased toward Figma, React, iOS, or Android. Agents enter after deterministic scripts have scaffolded the code contract; they “refine and polish.” His own extraction tools “use any agent stuff at all” in the negative: they are scripts, so regenerating an entire library has no token cost. [Nathan Curtis, interviewed by Don D'Amato, “Specs Made Spectacular,” Wireframe by Design Systems House, published 28 October 2026](https://exa.ai/library/podcast/t3g656dlr7n/episode/g11qn6nwdv7).
- Josef Richter, July 2026 state of the art: one canonical DTCG source; generated CSS and agent metadata are derived. Deprecation guidance belongs in the component’s `DESIGN.md` or in `AGENTS.md` plus a skill that names the canonical component and the class names that are off limits. His Button example includes “Do not author new Surface `<Button>` markup.” [Josef Richter](https://josefrichter.design/blog/agentic-design-system).
- Figma, “The Figma design agent is here,” Rodrigo Davies and Tammy Taabassum, publication date not stated on the fetched page: the canvas agent is for in-file work and is “built for direct manipulation so you can stay in control.” Use the canvas agent on the canvas; use MCP and `use_figma` to move between code and the canvas. For a design system, they describe the agent bulk-updating descriptions, tags, use cases, naming, and component documentation. During beta the agent does not consume credits. It is for Full seats on Professional, Organization, and Enterprise; Collab and Dev seats can use it in drafts; Starter, Education, and Government are excluded. Writing via the remote MCP outside drafts requires a Full seat; the write feature is described as free during beta and later usage-priced. [Figma Blog, “The Figma design agent is here”](https://www.figma.com/blog/the-figma-agent-is-here/); [Figma MCP introduction](https://developers.figma.com/docs/figma-mcp-server/).
- Aestheria, August 2026: as decisions move to the system, the operational question is whether a team can see the decision, override it, and roll it back. The post cites a June 2025 Gartner press release predicting that over 40% of agentic AI projects would be canceled by the end of 2027, with inadequate risk controls among the causes, and the phrase “agent washing.” Aestheria’s recommended reading of that figure is a checklist: where the decision log lives, and what the rollback story is. [Aestheria, August 2026](https://aestheria.design/blog/what-is-an-agentic-design-system). A different Gartner figure is cited by Romina Kavcic in the Into Design Systems guide: “40% of enterprises will use AI agents by end of year.” [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems). These are not the same claim. The Gartner primary release was not fetched.
- Knapsack CEO Chris Strahl, in a Unite AI Q&A indexed in search (publication date not on the snippet; the full article was not fetched): enterprises need provenance, ownership, permissions, and audit logs so leaders can trust automated workflows. He says teams must author constraints, policies, and component contracts in a form agents can use, plus rollout controls and observability of agent decisions. Treat this as a vendor interview, not a neutral standard. [Knapsack, “Unite AI Q&A with Chris Strahl”; date not confirmed](https://www.knapsack.cloud/blog/unite-ai-q-a-with-chris-strahl).

#### Conflict on whether an agent may merge or publish

- Suggest-only or issue-only for anything that changes the system: Jan Six / Primer, as reported, agents never merge. Romina’s reported model reserves auto-merge for lint, typos, and accessibility labels, and bars auto-merge for APIs, breaking changes, and governance. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- Draft by default, merge allowed after a subset test: zeroheight MCP-Write. Sidbury explicitly says bulk automations that skip manual review are not blocked, if the team asks the agent to merge. [Seb Sidbury, 15 October 2026](https://zeroheight.com/blog/mcp-write-what-changes-when-ai-can-write-to-your-design-system/).
- Read-only first: Supernova’s MCP step says start read-only. [Supernova Part 2](https://www.supernova.io/blog/how-to-make-your-design-system-ai-ready).
- Scripts, not agents, for the spec and the version classification; agents only after the contract is scaffolded: Nathan Curtis, 28 October 2026. [Wireframe episode](https://exa.ai/library/podcast/t3g656dlr7n/episode/g11qn6nwdv7).

### Inferences

- The overlapping recommendation is: the agent acts with a named human’s permissions, writes a reviewable artifact (issue, draft, or PR), and does not become the owner of breaking changes. The disagreement is whether “reviewable” may be skipped after a trial, and whether the artifact is an issue or a draft page.
- “Who owns the system” is answered structurally (token owner, small publish group, ADRs) by Huntsberry, and as product permissions by zeroheight and Figma. No source in this set names a required org chart (design-system lead vs staff engineer vs a new AI owner).

### Gaps

- No source retrieved here specifies a full deprecation policy for agent-proposed components (sunset window, codemod ownership, when an agent may delete a token). The concrete pieces are: same-release deprecation across Figma and code (Huntsberry), deprecation called out in `AGENTS.md` and MCP (Supernova), and breaking/minor/patch classification of a Figma branch (Curtis).
- Chris Strahl’s Q&A was not fetched in full, so date, and any caveats around the quotes, are unverified.
- The two Gartner “40%” figures were not checked against Gartner’s own pages.

## What evaluation practice do sources recommend?

### Takeaway

The strongest shared recommendation is that a model reviewing its own output is not an evaluation. Checks should be deterministic where the rule can be closed (token membership, props, deprecation, contrast) and should include a benchmark of the retrieval format before the team standardizes on it. Visual comparison, accessibility review, and golden-style prompt sets are described in case studies, not as one industry-standard harness.

### Cited Findings

#### What sources say teams should do

- Aestheria, August 2026: an agent that generates, reviews itself, and ships “has not evaluated anything. It has agreed with itself.” Evaluation needs a standard outside the thing evaluated. That standard is the computational layer: greys as a closed set a value can fail to belong to; a usage guideline as a condition a build can break on, not a paragraph. The post names what to verify against: the token set, density and spacing rules, contrast floors, component contracts, and the states a pattern is allowed to have. If the only check is “a designer looks at it,” Aestheria calls that a review process, not a system. The same post marks three cells unsolved for agentic systems as of August 2026: explaining a specific decision at runtime, what output is verified against in shipped products, and recourse when wrong. [Aestheria](https://aestheria.design/blog/what-is-an-agentic-design-system).
- Diana Wolosin’s reported harness is a retrieval benchmark, not a visual regression suite: 1,056 prompts, 8 MCP configurations, measured accuracy, token use, and cost, on 77 components. The recommendation is to run that kind of comparison before committing to Markdown, JSON, or a hybrid. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- Spotify Encore, as reported: a custom MCP evaluation framework that runs prompts against multiple LLMs and compares generated components both in code and visually. The line attributed to the team is “We can’t just launch and hope for the best.” The architectural change that preceded useful evals, as reported, was splitting components into foundation, style, and behavior layers so the model gets smaller context. Reported outcomes attached to that architecture, not proven in these notes as caused by the eval harness: 220,000+ shared style uses, 93% developer satisfaction. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents); [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems).
- Brad Frost Web and Southleft, as reported in the conference guide: the FigmaLint plugin runs deterministic and AI analysis, scores a component (an example moved from 26/100 to 100/100 after fixes), and checks token usage, layer naming, accessibility, and component descriptions. [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems). This is not in Frost’s 16 December 2025 post.
- Romina Kavcic’s Tidy plugin, as reported: 66 MCP tools that audit naming, score health in six categories, validate new variables, and compose patterns only from existing components. Observatory is described as a dashboard over Figma, GitHub, Storybook, Linear, Chromatic, Playwright, and PostHog. The self-healing loop she describes (Observe, Detect, Suggest, Fix, Learn, mapped to IBM’s 2003 MAPE-K) takes signals from the Figma API, CI hooks, and usage analytics, scores drift, and opens PRs. [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems).
- Jan Six, as reported: a dedicated accessibility-reviewer sub-agent, plus daily QA whose only write action is opening an issue. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- Huntsberry, “what good looks like,” no page date: visual regression in CI for design/code parity; documented parity exceptions with owners; token pipelines that propagate a Figma change within a release cycle; drift treated as a defect. Accessibility (focus, keyboard, ARIA, contrast) tested in CI. He does not publish a golden-task set. [Matthew Huntsberry](https://www.mmhuntsberry.com/methodology).
- zeroheight, Sidbury, 15 October 2026: an agent can audit a styleguide against a page template and check for Do/Don’t rules, a complete properties table, accessibility guidance, and required blocks. Separately, the MCP product page says teams can run a structured audit before handover or merge so agents flag off-system design and code. That is a vendor description of the product, not an independent case study. [Seb Sidbury, 15 October 2026](https://zeroheight.com/blog/mcp-write-what-changes-when-ai-can-write-to-your-design-system/); [zeroheight MCP](https://zeroheight.com/mcp/).
- Nathan Curtis, 28 October 2026: once a spec exists, scripts analyze props, styling, dependencies, and naming “to track and sustain coherence,” and classify a proposed Figma merge as breaking, minor, or patch. He argues this class of check should not be an agent call. [Wireframe, 28 October 2026](https://exa.ai/library/podcast/t3g656dlr7n/episode/g11qn6nwdv7).
- Supernova’s five-check rubric is an evaluation of whether an agent can resolve the system, not of whether generated UI is correct. Bands: 0–3 Readable, 4–6 Partly resolvable, 7–10 Resolvable. A low score “says nothing about how good a design system is for the people using it.” [Supernova, 5–6 October 2026](https://www.supernova.io/blog/ai-ready-design-systems-2026-study).
- The Supernova “preparing” article (date not stated) lists linting, usage dashboards, and anomaly detection as the validation focus area. It does not specify visual regression or an agent eval harness. [Supernova, preparing article](https://www.supernova.io/blog/ai-ready-design-systems-preparing-your-design-system-for-machine-powered-product-development).
- Knapsack’s marketing site says evaluation should measure conformance to the organization’s standards, design fidelity, code quality, and cost per shippable output, with provenance back to a source the organization controls. That is a vendor claim. No publication date, no published harness spec on the pages retrieved. [Knapsack homepage](https://www.knapsack.cloud/).
- Figma’s designer-facing MCP article: a screenshot tells a model what something looks like; structured data (hierarchy, auto-layout, variants, text styles, spacing, variable code syntax, Code Connect) tells it what something is. The same article says the MCP server cannot understand why a decision was made, replace judgment, or guarantee accurate code if the system is inconsistent. No publication date on the page. [Figma, “MCP for Designers”](https://www.figma.com/resource-library/mcp-for-designers/).

#### What sources say teams do today, where contrasted

- The common first eval, which Diana Wolosin’s benchmark is reported to have falsified: connect existing Markdown or MDX docs to an MCP and treat a plausible answer as success. Reported result: high token cost, incomplete coverage, hallucinations. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- Spotify, as reported: before the layered architecture, developers went to Cursor first, received non-Encore UI, and shipped it. The system was too large for the model to reason over, so it was bypassed rather than evaluated. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- Don D'Amato, interviewing Curtis, describes 2026 behavior he says he saw: in Q2 teams “put all the money in the agents,” and in Q3 CFOs pulled back because cost was unsustainable. Curtis’s contrast is a scripted pipeline with no token cost on regeneration. This is the host’s characterization, not a measured study. [Wireframe, 28 October 2026](https://exa.ai/library/podcast/t3g656dlr7n/episode/g11qn6nwdv7).

### Inferences

- “Golden tasks” as a named practice did not appear in the sources above. The closest published artifact is Indeed’s 1,056-prompt retrieval benchmark and Spotify’s multi-model prompt set with code and visual comparison. A roadmap can recommend those patterns without calling them an industry-standard golden-task suite.
- Token linting is recommended in pieces (FigmaLint token-usage checks, Huntsberry’s closed taxonomy, Supernova’s ban on hardcoded values, Richter’s semantic tier) and not as a single named linter everyone points to.
- Aestheria’s August 2026 “unsolved” verdict conflicts with conference speakers who describe working eval loops. The charitable reading, which is an inference: speakers have internal harnesses; Aestheria argues the field still lacks a shared, external, checkable standard and a recourse story. Both statements can stand.

### Gaps

- No primary write-up was retrieved that specifies a design-QA sampling rate, a visual-regression tool by name as the recommended default, or an accessibility automated-test baseline (axe versus manual) for agent output.
- Indeed’s and Spotify’s harnesses are known only through Into Design Systems. No Indeed or Spotify engineering post was fetched to confirm the numbers.
- FISYCO’s claim that rules files are context rather than enforcement was seen only in a search snippet and is not used as a finding.

## What should not be automated yet, according to design-system leads?

### Takeaway

Design-system leads, as quoted by Into Design Systems and on Curtis’s October 2026 podcast, tell teams not to automate judgment: new APIs, breaking changes, governance decisions, and the production of the spec itself. Vendor posts add a second list: do not treat a pre-1.0 agent format as a production dependency, do not let write-access MCP manage tokens or releases, and do not replace a human decision about why a design exists.

### Cited Findings

- Romina Kavcic, as reported: do not let agents “run in the wild.” Some decisions never go past her third trust level. Suggest-only, not auto-merge: new component APIs, breaking changes, and governance decisions. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents); [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems).
- Jan Six, as reported: Primer’s agents do not merge code. Their automated output is an issue a human reviews. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- Nathan Curtis, 28 October 2026: do not use an agent to regenerate specs from Figma. He contrasts “misting with a little handheld mister” (MCP, one component at a time) with a scripted download of the library that finishes in about a minute and costs no tokens. Agents come after scripts have scaffolded the contract, to refine and polish. He also rejects the early-2025 practice of screenshotting his specs plugin and pasting the image into a model; the replacement he wanted was JSON or YAML. [Wireframe, 28 October 2026](https://exa.ai/library/podcast/t3g656dlr7n/episode/g11qn6nwdv7).
- Brad Frost, 16 December 2025: unconstrained generation is vibe coding. The practice he endorses is generation deliberately constrained to the design system. He does not publish a list of tasks that must stay manual. [Brad Frost, 16 December 2025](https://bradfrost.com/blog/post/agentic-design-systems-in-2026/). His November 2025 course announcement says to treat AI with “simultaneous curiosity and skepticism,” and that AI “can make a huge mess” unless the design system keeps it on the rails. [Brad Frost, 24 November 2025](https://bradfrost.com/blog/post/introducing-our-new-course-ai-and-design-systems/).
- Aestheria, August 2026: do not count model self-critique as evaluation. Do not claim the reasoning loop, runtime explanation, or recourse is solved. The post says anyone claiming otherwise “deserves your follow-up questions.” [Aestheria](https://aestheria.design/blog/what-is-an-agentic-design-system).
- Josef Richter, July 2026: do not take `DESIGN.md` as a production dependency yet. Use it as a direction. Do not fork a second source of truth beside DTCG. Do not stop at primitive tokens whose meaning lives only in a `$description` string. [Josef Richter](https://josefrichter.design/blog/agentic-design-system).
- Seb Sidbury, zeroheight, 15 October 2026: do not automate the entire documentation process on day one. Do not bulk-merge until a subset has been tested. The write API, as shipped then, does not automate token management, releases, settings, new styleguides, or adding Figma and Storybook files. [Seb Sidbury, 15 October 2026](https://zeroheight.com/blog/mcp-write-what-changes-when-ai-can-write-to-your-design-system/).
- Figma’s MCP article for designers: the server cannot replace judgment or explain why a decision was made. [Figma, “MCP for Designers”](https://www.figma.com/resource-library/mcp-for-designers/). The help center: the server does not, by itself, finish code. [Figma Help Center, MCP FAQs](https://help.figma.com/hc/en-us/articles/39252411778583-Figma-MCP-server-FAQs).
- Chris Strahl, date not confirmed, vendor Q&A: agents should take repetitive work (scaffolding pages, proposing accessible variants, localized content). Designers should keep strategy, experience intent, edge-case UX, and the constraints. Engineers should keep component correctness, runtime contracts, observability, and performance. Humans “define the rules, review outputs, and determine what quality looks like.” [Knapsack, Chris Strahl Q&A; date not confirmed](https://www.knapsack.cloud/blog/unite-ai-q-a-with-chris-strahl).

### Inferences

- “Not yet” in this literature usually means “not without an external check and a human on the merge,” not “never use a model.” Curtis is the sharpest exception: spec extraction and release classification should stay deterministic even when models are available.
- Sidbury’s permission to auto-merge documentation drafts after a subset test is narrower than it sounds. It is styleguide prose, and it excludes tokens and releases. It does not license auto-merge of component APIs, which Romina’s model keeps at suggest-only.

### Gaps

- No design-system lead in the sources retrieved published an explicit “do not automate yet” list covering visual design exploration, brand, content tone, or research synthesis. Strahl’s split (strategy and edge cases stay human) is the closest, and it is a vendor interview without a confirmed date.
- Frost’s course is described as the place that teaches judgment. The course itself is paid, and its module-level “do not automate” guidance was not public on the pages fetched.

## What organizational mistakes are repeatedly cited?

### Takeaway

The mistakes that show up in more than one independent source are: connecting human prose to an agent without a structured contract, letting documentation and tokens disagree, omitting semantic tokens, skipping a contribution path so agent changes bypass review, and writing agent instructions for the design-system team while product teams’ agents receive nothing. Dumping an entire Figma file into a prompt, and treating the chatbot UI as the design system, were not found as repeated citations in those words.

### Cited Findings

- Plugging existing Markdown into an MCP without a benchmark. Called “the most common first move” by Sil Bormüller, citing Diana Wolosin’s Indeed benchmark (about 30,000 tokens per query, 82% coverage, hallucinations, versus JSON). [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- Documentation drift: docs, tokens, and components disagree, and an agent cannot tell which source is right. Romina Kavcic, as reported, said 30–40% of design-system team time goes to maintenance, including accessibility regressions, token misuse, and docs out of sync. The agent then picks the first source or averages them. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- No semantic layer. Huntsberry’s “what broken looks like”: a flat palette named `gray-400`, referenced directly by components; the same name meaning different things; Figma variables and CSS custom properties named differently; designers shipping hex because the right token does not exist. [Huntsberry](https://www.mmhuntsberry.com/methodology). Jan Six, as reported: use `danger.background`, not raw `red-500`. [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems). Richter, July 2026: primitives plus a human-readable `$description`, with no semantic reference and no component tier, is “the single most common real-world shortcut.” A second gap he names: tokens authored, then components that hard-code arbitrary radius and spacing instead of consuming those tokens. [Josef Richter](https://josefrichter.design/blog/agentic-design-system).
- No contribution model for AI changes. Huntsberry: “AI-assisted contributions that bypass review because the process was not designed for them.” Also: decisions made in Slack and never recorded; accessibility delegated to product teams “to add later.” [Huntsberry](https://www.mmhuntsberry.com/methodology).
- Agent instructions written for the wrong audience. Supernova, 5–6 October 2026: 12 of 31 public systems have `AGENTS.md`, and all 12 tell contributors how to install, test, and open a PR. None tells a consuming product team how to use the system. Fourteen systems have contributor-only agent instructions; three have consumer guidance. Unofficial MCP servers for GOV.UK, USWDS, and Fluent UI are described as a demand signal and a risk, because an unofficial server can drift from the system with no way for users to tell. [Supernova study](https://www.supernova.io/blog/ai-ready-design-systems-2026-study).
- MCP without always-on foundation rules, so components are “right” and spacing, type, and color are invented. Attributed to Brad Frost in the conference write-ups, not in his December 2025 post. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- Monolithic component definitions. Spotify Encore, as reported: one file with props, styles, behavior, accessibility, and usage guidelines led agents to bypass the system. Developers asked Cursor first and shipped non-Encore UI. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents). Supernova’s undated “preparing” article makes a related recommendation: scope context per consumer, because the whole system in the window performs worse. [Supernova, preparing article](https://www.supernova.io/blog/ai-ready-design-systems-preparing-your-design-system-for-machine-powered-product-development).
- Screenshot or canvas output where a spec is possible. Curtis, 28 October 2026: at the beginning of 2025 people screenshotted his Figma specs plugin and fed the image to a model. He says to feed JSON. He also says design intent will not be captured by a canvas page of anatomy callouts once machines are the consumers. [Wireframe, 28 October 2026](https://exa.ai/library/podcast/t3g656dlr7n/episode/g11qn6nwdv7). Figma’s own designer article says a screenshot tells the model appearance and structured data tells it identity, and that a messy system will not yield accurate code. [Figma, “MCP for Designers”](https://www.figma.com/resource-library/mcp-for-designers/).
- Giving an agent merge rights with no trust levels. Sil Bormüller states this as a failure mode: the agent merges PRs, updates tokens, and edits APIs, including changes that needed a human. [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- Treating generation as the system. Aestheria, August 2026: an agent or a generator without the rules layer produces plausible UI, or variety, with nothing that can fail a check. [Aestheria](https://aestheria.design/blog/what-is-an-agentic-design-system). Figma’s help center: the MCP server is not itself the coder, and the agent does not know conventions that were not supplied. [Figma Help Center, MCP FAQs](https://help.figma.com/hc/en-us/articles/39252411778583-Figma-MCP-server-FAQs).
- Huntsberry’s broken Figma architecture, which agents then repeat as if it were the system: multiple overlapping libraries, variant axes that do not exist in code, forks in product files, no record of detached instances. [Huntsberry](https://www.mmhuntsberry.com/methodology).

### Inferences

- “Dumping the whole Figma file into a prompt” is a fair paraphrase of two cited failures (screenshot-the-canvas, and letting an agent crawl variants because no spec exists), but it is not a phrase these sources use. Curtis actually wants the whole library processed, by a script, into a spec. The mistake he names is the screenshot and the per-component MCP poke, not “never read the whole file.”
- “The chatbot UI is the design system” was not found. The nearest cited mistakes are: the MCP server is not the system (Figma), the agent is not the logic layer (Aestheria), and contributor `AGENTS.md` is not consumer guidance (Supernova).

### Gaps

- No source retrieved uses the sentences “do not dump the whole Figma file into a prompt” or “do not treat the chatbot UI as the design system.” Those should not be cited as quotations.
- A repeated citation across Frost, Curtis, and zeroheight of one shared mistake list was not found. Overlap was reconstructed by comparing sources, which is why several bullets name a single source.
- Nathan Curtis’s Substack “Figma Component Specs on Command” was not fetched (likely paywalled). A search snippet said an agent spent minutes reading 45 variants one by one. That anecdote is not quoted above because the full post was not read.

## Are there public checklists, RFCs, or reference architectures for small teams and for large design orgs?

### Takeaway

Public checklists exist and are usable by a small team: Supernova’s five checks and five steps, Huntsberry’s eight pillars, Designesy’s ten checks, and zeroheight’s “start with one workflow.” A format sketch aimed at agents, `DESIGN.md`, is described by Richter as pre-1.0 as of July 2026. No RFC was found that is written for a 1–10 person design/engineering team. Large-org reference stories in this set are Indeed, GitHub Primer, Spotify Encore, and New York State, all secondhand via Into Design Systems, plus Supernova’s scoreboard of 31 public systems.

### Cited Findings

#### Small-team or any-size public artifacts

- Supernova Part 2 is the most concrete public checklist retrieved: five steps, with effort estimates (an afternoon, a day or two, a few days, “depends,” and MCP as the big job). The first two steps are described as about a week. The rubric is intentionally checkable from packages, a repo, and a docs site. Supernova says the same Claude skill can score a private system and asks the three enterprise questions public repos cannot answer (access control, adoption data, governance). Supernova also says its hosted MCP lookups are unlimited on every plan, including free. That last sentence is a vendor offer. [Supernova Part 2](https://www.supernova.io/blog/how-to-make-your-design-system-ai-ready); [Supernova study, 5–6 October 2026](https://www.supernova.io/blog/ai-ready-design-systems-2026-study).
- Huntsberry’s eight pillars are written for design-system leads, VPs of Design, and heads of engineering. He says he ran the model on an early-stage product team’s two Figma libraries and a coded library, and that the score sent them into a rebuild of the variable architecture. The case study itself was not fetched. No page date. [Huntsberry](https://www.mmhuntsberry.com/methodology).
- Designesy’s ten-check contract is a public, automatable score. It cites zeroheight 2026 as the maturity axis it implements. Several checks (`robots.txt`, Open Graph) are website hygiene, not design-system governance. No page date. [Designesy](https://www.designesy.org/contracts/readiness).
- zeroheight’s maturity book advertises a self-assessment worksheet for all six axes, including AI Readiness, plus nine archetypes. The worksheet is not reproduced on the public page. [zeroheight, Measuring Design System Maturity](https://zeroheight.com/resource/measuring-design-system-maturity/). Sidbury’s getting-started list is a small-team sequence: pick one workflow, connect MCP via login, connect source systems, provide a template, use a skill or a prompt, review the draft, then expand. [Seb Sidbury, 15 October 2026](https://zeroheight.com/blog/mcp-write-what-changes-when-ai-can-write-to-your-design-system/).
- Aestheria’s three-item list (rules that can fail, a named verification standard, a recourse story) is size-agnostic and explicitly includes teams that do not yet have a design system. August 2026. The rest of that post is also a product argument for Aestheria’s own context layer. [Aestheria](https://aestheria.design/blog/what-is-an-agentic-design-system).
- Richter’s reference pipeline (DTCG → Style Dictionary → MCP intent metadata → Code Connect, with `DESIGN.md` downstream and still alpha) is written as a single-component walkthrough a small team could copy. He illustrates it on Elixir/Phoenix, not on a large design org. July 2026 state-of-the-art section. [Josef Richter](https://josefrichter.design/blog/agentic-design-system).
- The Into Design Systems “how to start” list is explicitly “starting Monday” and says immature systems can begin with naming, tokens, and descriptions. [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems).
- Figma’s MCP docs are a product reference, not an adoption RFC. They apply to any team that can connect a supported client. Writing outside drafts is Full-seat-gated. [Figma MCP introduction](https://developers.figma.com/docs/figma-mcp-server/).

#### Large-org reference material

- Supernova’s 31-system table is the only large comparative architecture snapshot retrieved. Top scores on 5–6 October 2026: Ant Design, Atlassian Design System, and React Spectrum at 9 out of 10, each missing consumer guidance. Carbon (IBM) at 8. Primer (GitHub) at 7, with an official MCP and contributor-only guidance, and no `llms.txt` credit. The study says a low score is not a quality judgment of the human system. [Supernova, 5–6 October 2026](https://www.supernova.io/blog/ai-ready-design-systems-2026-study).
- Conference case studies, secondhand: Indeed (JSON metadata for 77 components, retrieval benchmark, 4,300 AI prototypes in 4 months); GitHub Primer (public MCP, instruction files, issue-only agents, accessibility sub-agent); Spotify Encore (foundation/style/behavior layers, multi-LLM eval with visual and code comparison); New York State (Jesse Gardner: Lit and TypeScript, Code Connect, a custom MCP with JSDoc usage guidance; a 5-page PDF turned into a styled multi-step form in 13 minutes in the demo). [Into Design Systems guide](https://www.intodesignsystems.com/agentic-design-systems); [Sil Bormüller, 10 April 2026](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents).
- Curtis’s pipeline is aimed at library-scale regeneration (he demonstrates the idea on GitHub Primer in a LinkedIn description that was not treated as a primary spec here) and at enterprises via “code factories” that consume a versioned spec. The primary source actually read is the 28 October 2026 podcast. [Wireframe](https://exa.ai/library/podcast/t3g656dlr7n/episode/g11qn6nwdv7).
- Knapsack positions its MCP and “Intelligent Product Engine” at enterprise teams, with permissions, auditability, and conformance checks. Vendor marketing; no public RFC. [Knapsack homepage](https://www.knapsack.cloud/); [Knapsack, “The Intelligent Product Engine,” date not confirmed in this pass](https://www.knapsack.cloud/blog/the-intelligent-product-engine-how-mcp-powers-contextual-ai-workflows).

#### Formats that are not quite RFCs

- `DESIGN.md`, as described by Richter: Google Labs, April 2026, YAML tokens plus Markdown rationale, meant to sit with `AGENTS.md` and `SKILL.md`. He says it is pre-1.0 and not a safe production dependency. The GitHub fetch in this research did not return the specification body, so this note does not treat DESIGN.md as a verified standard. [Josef Richter](https://josefrichter.design/blog/agentic-design-system).
- DTCG, as described by Richter: stable token-format module v2025.10, 28 October 2025. Not an agentic-design-system RFC. Not re-verified on the DTCG site. [Josef Richter](https://josefrichter.design/blog/agentic-design-system).
- `llms.txt` is used as a convention by Supernova and Designesy. Neither source presents it as a design-system RFC. [Supernova Part 2](https://www.supernova.io/blog/how-to-make-your-design-system-ai-ready); [Designesy](https://www.designesy.org/contracts/readiness).

### Inferences

- For a 1–10 person team, the sources that can be followed without a conference pass or a paid course are Supernova’s five steps, Huntsberry’s score, Richter’s DTCG-first pipeline, Aestheria’s three preconditions, and Sidbury’s single-workflow start. None of those authors labels the artifact “for teams of 1–10.”
- For a large org, the public comparison set is Supernova’s table. The operating-model detail (trust levels, issue-only agents, retrieval benchmarks, layered components) is still trapped in conference retellings rather than in owner-published RFCs.

### Gaps

- No RFC, W3C note, or public GitHub RFC was found whose stated audience is a 1–10 person design and engineering team adopting an agentic design system.
- Schema by Figma, Clarity, and Knapsack conference talks were not retrieved as primary transcripts. YouTube searches were not run as a separate pass; written versions of the talks were used where Into Design Systems had published them.
- zeroheight’s worksheet and archetype guidance were not available without the book.
- Owner-published architecture posts from Indeed, Spotify, and GitHub Primer were not fetched, so those case studies remain secondhand.

# Agent-consumable design systems

Scope note for the report writer: this file covers the machine-readable design system (tokens, components, documentation, MCP servers, Code Connect mappings, agent rules, and evals) as of 21 November 2026. It does not cover UX patterns of agent products. "Shipping practice" below means an official doc, a named company's engineering post, or a public repository whose tool catalog and file format can be read. Vendor READMEs that describe what their product "solves" are labeled as product claims. No adoption survey was found, so "prevailing" is an inference from which interfaces official docs and public implementations repeat, not a market-share statistic.

## What is the prevailing stack in 2025–2026?

### Takeaway
The stack that official docs and public implementations actually share is DTCG JSON (2025.10) for tokens, a build step such as Style Dictionary to emit platform values, a component catalog the agent must query (Storybook manifests, a shadcn registry, Figma libraries plus Code Connect, or a design-system MCP server), and a short rules file (`AGENTS.md`, `CLAUDE.md`, or Cursor rules) that points at those tools. React is the framework with the most first-party agent tooling. There is no published survey that this combination is what most teams run.

### Cited Findings
- The Design Tokens Community Group published Design Tokens 2025.10 on 28 October 2025 as the first stable version: three modules (Format, Color, Resolver), a JSON file with `$type` and `$value`, and resolver documents whose `version` must be `2025.10` for themes and modes. The status section says it is a Final Community Group Report, "not a W3C Standard nor is it on the W3C Standards Track." Editors named on the Format module include Louis Chenais, Kathleen McMahon, Drew Powers, Matthew Ström-Awn, and Donna Vitan. — [Design Tokens Technical Reports 2025.10](https://www.designtokens.org/tr/2025.10/); [Format module](https://www.designtokens.org/tr/2025.10/format/); [Resolver module](https://www.designtokens.org/tr/2025.10/resolver/); [DTCG announcement, 28 October 2025](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/)
- The same DTCG announcement names Style Dictionary, Tokens Studio, and Terrazzo as reference implementations, and says more than 10 tools "already support or are implementing" the standard, listing Penpot, Figma, Sketch, Framer, Knapsack, Supernova, and zeroheight. That sentence is the community group's claim about tool support, not a compatibility matrix. — [DTCG announcement, 28 October 2025](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/)
- Style Dictionary's own tokens page says version 4 is forward-compatible with the DTCG format: DTCG uses `$value`, `$type`, and `$description`; the original Style Dictionary format uses `value`, `type`, and `comment`. "In version 4 you can use either format, pick one though as they cannot be combined inside a single Style Dictionary instance." The page, as fetched, does not state a release date or claim full 2025.10 module coverage. — [Style Dictionary, Design Tokens](https://styledictionary.com/info/tokens/)
- Figma's Schema 2025 recap says Figma waited for the DTCG "1.0 release" before shipping native variable import and export, and that "Variables import and export will be available in November." — [Figma Blog, Schema 2025: Design Systems For A New Era](https://www.figma.com/blog/schema-2025-design-systems-recap/)
- A Figma forum thread opened 25 November 2025 reports that extended collections had shipped but "Export modes" was not yet visible. A Figma reply dated 4 December 2025 (account `djv`) says the feature "is still being rolled out." — [Figma Forum, Native variable export feature](https://forum.figma.com/ask-the-community-7/native-variable-export-feature-47831)
- A secondary writeup dated as checked against Figma help on 31 October 2026 says the built-in path is Variables panel → right-click a collection → Export modes, and that Figma's import help accepts a limited DTCG subset: `color` only as HSL or sRGB, `dimension` only in `px`, `duration` only in `s`, `fontFamily` as a single name. This research did not re-fetch the Figma help page, so the type limits are that author's reading. — [UIX, How to export Figma variables as DTCG JSON](https://useuix.com/blog/export-figma-variables-dtcg-json)
- Figma's remote MCP server is documented at `https://mcp.figma.com/mcp`. Design-system read tools include `get_libraries`, `search_design_system` (components, variables, and styles), `get_code_connect_map`, `get_design_context` (default output React + Tailwind), `get_metadata` (lightweight XML when the selection is too large), `get_screenshot`, and `get_variable_defs` (variables and styles used in the selection). One MCP prompt, `create_design_system_rules`, drafts a rules file to save under `rules/` or `instructions/`. Page undated as fetched. — [Figma Developer Docs, Introduction](https://developers.figma.com/docs/figma-mcp-server/); [Tools and prompts](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)
- When Code Connect mappings exist, `get_code_connect_map` returns, per instance, `componentName`, `source` (file path or URL), `snippet` / `snippetImports` / `snippetNestedFunctions` when available, `version` (UI or CLI), and `label` (for example `React`). The remote server selects mappings with `clientFrameworks` and `clientLanguages`. Code Connect requires a Full or Dev seat on Professional, Organization, Government, or Enterprise, and components that are already connected. Page undated as fetched. — [Figma Developer Docs, Tools and prompts](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/); [Code Connect integration](https://developers.figma.com/docs/figma-mcp-server/code-connect-integration/)
- Storybook's MCP server is an addon, `@storybook/addon-mcp`, served at `http://localhost:6006/mcp` while the dev server runs. Docs tools (`docs-list`, `docs-show`, `docs-show-story`) read a components manifest. As documented, the manifest and a component API in `docs-show` exist for every React framework Storybook ships (`react-vite`, `react-webpack5`, `nextjs`, `nextjs-vite`, `tanstack-react`, `react-native-web-vite`), for `@storybook/angular-vite`, and for `@storybook/vue3-vite` if `experimentalDocgenServer` is also on. Webpack Angular and other frameworks have no manifest, so the docs toolset is unavailable. The feature is marked "in preview." Page undated as fetched. — [Storybook docs, MCP server](https://storybook.js.org/docs/ai/mcp/overview)
- Storybook's blog post by Kyle Gach, 23 March 2026, updated 11 September 2026, says Storybook MCP "is available now in Storybook 10.3 for React projects" and that "MCP support for other frameworks [is] coming later this year." A published Storybook can expose the docs tools without a local Storybook; Chromatic "supports publishing Storybook MCP." — [Kyle Gach, Storybook MCP for React, 23 March 2026](https://storybook.js.org/blog/storybook-mcp-for-react/); [Storybook docs, Use a published Storybook](https://storybook.js.org/docs/11/ai/published-storybook)
- shadcn/ui's official MCP server browses, searches, and installs items from registries listed in `components.json`, including the public shadcn registry, third-party registries that follow the shadcn registry spec, private registries, and `@namespace` registries. Documented clients are Claude Code (`.mcp.json`), Cursor (`.cursor/mcp.json`), VS Code (`.vscode/mcp.json`), and Codex (`~/.codex/config.toml`), all launching `npx shadcn@latest mcp`. The page does not document a token file or a prop schema. Page undated as fetched. — [shadcn/ui, MCP Server](https://ui.shadcn.com/docs/mcp)
- v0's Design Systems 2.0 stores a design system as a skill: "not a copy of your docs; it is an adapter that tells v0 where your source lives, which components, props, and tokens are safe to use, and how to wire the system into new apps." Expected inputs are an installable package, the design-system repo, a real consuming app, Storybook or docs, and optional Figma frames. The API loads it as a `memory` skill (`scope: 'team' | 'user'`, `skillName`). Up to three skills can be passed per request. Pages undated as fetched. — [v0, Design Systems 2.0](https://v0.app/docs/design-systems-2); [v0 API, Design Systems](https://v0.app/docs/api/v2/guides/design-systems)
- Claude Code loads `CLAUDE.md` at session start and treats it as context, "not enforced configuration." Blocking an action requires a PreToolUse hook. Recommended size is under 200 lines per `CLAUDE.md`; longer files "consume more context and reduce adherence." Auto memory loads the first 200 lines or 25KB. `AGENTS.md` is read by default only when no `CLAUDE.md` or `CLAUDE.local.md` exists in the working directory or above it, and direct `AGENTS.md` reading requires Claude Code v2.1.277 or later. Page undated as fetched. — [Anthropic, How Claude remembers your project](https://code.claude.com/docs/en/memory)
- Public design-system MCP servers repeat the same tool shapes: list/search/get component, get/search/resolve token, sometimes contrast or guideline fetch. Examples with readable catalogs: Adobe `@adobe/design-data-mcp` (embedded Spectrum snapshot, no network for lookups), Basalt (`get_token`, `get_component`, tokens "stored in Git as DTCG 2025.10 JSON"), Sekura Design MCP (DTCG export among other formats), `ds-mcp` (a `dspack` JSON file), and `ds-pilot` (scans React/Vue components and DTCG JSON, nested JSON, or CSS custom properties). — [Adobe, Using AI](https://opensource.adobe.com/spectrum-design-data/ai/); [Basalt MCP.md](https://github.com/basalt-run/design-system/blob/main/MCP.md); [SekuraDesignMCP](https://github.com/mictsi/SekuraDesignMCP); [ds-mcp](https://github.com/OyaAIProd/ds-mcp); [ds-pilot](https://github.com/lyse-labs/ds-pilot)

### Inferences
- The practical 2025–2026 pipeline is: author tokens (Figma variables and/or DTCG JSON) → compile with Style Dictionary or an equivalent → expose components through a query tool (Storybook manifest, registry, Code Connect, or a design-system MCP) → constrain the agent with a short rules file. Teams that only paste a long prose style guide into the prompt are outside what these official docs describe.
- React is the path of least resistance because Storybook's component API, shadcn's registry, v0's package input, and Figma's default `get_design_context` output all assume it. Vue and Angular are partial. SwiftUI appears as a Code Connect label, not as a documented MCP catalog.
- Radix is not, in the sources found, an agent-facing format. The agent-facing layer that showed up on top of the popular React kit is the shadcn registry and its MCP server.

### Gaps
- No adoption survey, conference census, or vendor-neutral count of how many teams run DTCG plus Style Dictionary plus an MCP server. "Prevailing" is inferred from documentation and public repos.
- This research did not verify a specific Style Dictionary release (including any v5 claim) against GitHub releases. A secondary blog says v5.6.1 shipped 10 October 2026 and that full 2025.10 support was still incomplete; that was not checked against Style Dictionary's own release notes. — [Design tokens in 2026 (secondary)](https://maniruzzamanjubayer.com/blog/design-tokens-guide)
- Figma's exact exported JSON (whether every mode, alias, description, and scope survives, and the official type matrix) was not re-fetched from Figma Help. The UIX post is the only source here for import type limits.
- No 2025–2026 primary source was found that tells agents to call Radix primitives directly. shadcn's MCP page does not mention Radix.
- Documentation-site products named in the DTCG announcement (zeroheight, Supernova, Knapsack) were not found, in these searches, publishing an agent/MCP contract. Storybook is the documentation product with a first-party MCP server in the sources above.

## Which companies or open-source projects have published an agent-facing architecture?

### Takeaway
Two named organizations have published concrete contracts: Adobe (Spectrum Design Data, open source, read tools plus a draft agent-surface spec) and Gusto (Workbench, Zod schemas with `.meta()`, MCP, Braintrust evals). Storybook published both the product and an earlier RFC for component manifests. Several open-source servers publish tool catalogs and "do not invent" rules. Evidence of how Shopify, GitHub, Atlassian, IBM, or Salesforce expose their systems to agents was not found in this pass.

### Cited Findings
- Adobe's agent-readable surface spec is version `1.0.0-draft`. Status text: "Implemented — RFC-C / Phase 8 (epic #830). Core read/validate/write surface shipped." `write_component` is "not yet implemented." `explain` / `get_guidance` is "pending." The contract is three transports over one resolver: CLI (`design-data`), MCP (`@adobe/design-data-agent-mcp`), and a Claude Code skill. Normative operations include `primer`, `resolve_token`, `query_tokens`, `validate_usage`, `describe_component`, `diff_datasets`, and `write_token`. `suggest_token` and `token_refinements` are recommended, not required. The surface "returns structured tokens" and does not generate finished Swift or CSS. — [Adobe, Agent-readable surface](https://opensource.adobe.com/spectrum-design-data/spec/agent-surface/)
- Adobe's session `primer` must return `specVersion`, `manifest`, `modeSets`, `components`, `taxonomyFields`, `tokenTiers`, `semanticSpecificity`, and `tokenCount`. The spec recommends the primer fit in 2,000 tokens of context, with a `--summary` mode if it does not. Rationale, quoted: "The primer replaces the 'DESIGN.md emit' approach explored in earlier RFC-C drafts. A live, queryable primer keeps the agent's session context current without requiring the agent to maintain a frozen prose summary that can drift from the dataset." — [Adobe, Agent-readable surface](https://opensource.adobe.com/spectrum-design-data/spec/agent-surface/)
- Adobe's published `describe_component` example is kebab-case `name: "button"`, `displayName: "Button"`, options such as `variant` with values `accent`, `negative`, `primary`, `secondary` (default `accent`), anatomy parts (`icon`, required `label`), and states (`hover`, `keyboard-focus`, `disabled`) with trigger and precedence. A `relationships` object carries token bindings when present. The read-only Spectrum server looks components up "by kebab-case ID" and resolves tokens for a mode context of `colorScheme`, `scale`, and `contrast`. `design-data-suggest` ranks tokens with Jaccard similarity. — [Adobe, Agent-readable surface](https://opensource.adobe.com/spectrum-design-data/spec/agent-surface/); [adobe/spectrum-design-data, design-data-mcp README](https://github.com/adobe/spectrum-design-data/blob/main/tools/design-data-mcp/README.md)
- Adobe's consumer-facing server `@adobe/design-data-mcp` embeds a Spectrum snapshot, needs Node.js 20.12+, and is read-only. Guidelines "are an imported copy of public Spectrum site content and may lag it." The npm page for `@adobe/design-data-agent-mcp` lists author Adobe, created 2026-05-31, updated 2026-11-20. Those dates and the download count on that page are registry metadata, not an adoption study. — [Adobe, Using AI](https://opensource.adobe.com/spectrum-design-data/ai/); [npm, @adobe/design-data-agent-mcp](https://www.npmjs.com/package/@adobe/design-data-agent-mcp)
- Adobe's authoring workflow page says MCP authoring sessions (`start_authoring_session`, `edit_token`, `authoring_session_commit`, and related token/mode tools) write `*.tokens.json` and have shipped. "Component/field/registry authoring not yet shipped." — [Adobe, Authoring workflow](https://opensource.adobe.com/spectrum-design-data/spec/authoring-workflow/)
- Gusto's Jay Johnson (Builder Enablement; Medium byline Jaywritescode) describes Workbench's agent contract in two posts, 27 July 2026 and 3 August 2026. Each component has a Zod schema whose `.meta()` holds `examples` (snippets validated against the same schema), `contentGuidelines`, `accessibilityGuidelines`, `importStatement`, and `figmaUrl`. Button and Select use Zod unions with `.strict()` so illegal combinations (the example: a neutral tone with an outline variant) cannot be represented. The prompt discipline Johnson states: "copy from .meta().examples. Don't invent." Schemas "are published in a form any MCP-capable AI client can fetch." The illustrative import in part 1 is `import { Button } from '@acme/design-system'`; the failure diff in part 2 uses `@gusto/design-system`. — [Jay Johnson, Eval-Driven Design Systems (Part 1), 27 July 2026](https://engineering.gusto.com/eval-driven-design-systems-8f781dc2dacb); [Part 2, 3 August 2026](https://engineering.gusto.com/eval-driven-design-systems-part-2-5b989d492281)
- A FITC abstract for 28 October 2026, speaker Daniel Flynn, says Gusto's Workbench contracts back "a prompt-to-UI assistant, an app-like sandbox, MCP tooling, and Chat UI," and that Chat UI "uses schema composition" to stay connected to Workbench. The abstract does not include schemas or metrics. — [FITC, Schema-Driven Design Systems, 28 October 2026](https://fitc.ca/presentation/schema-driven-design-systems/)
- Storybook's August 2025-era RFC (discussion on `storybookjs/ds-mcp-experiment-reshaped`) proposed per-component JSON manifests (name, descriptions, props with types/defaults, story snippets, MDX) and an MCP with list, get-details, and keyword search, so a consumer app can point at `node_modules`, a local build, or a published Storybook URL. The shipping docs match that shape: `docs-list`, `docs-show` (props, the first three stories, an index of the rest), `docs-show-story`. The RFC is a design record; the docs page is the shipped surface, and the docs mark the API as preview. — [Storybook RFC discussion](https://github.com/storybookjs/ds-mcp-experiment-reshaped/discussions/1); [Storybook docs, MCP server](https://storybook.js.org/docs/ai/mcp/overview)
- `ds-mcp` (repo `OyaAIProd/ds-mcp`) is a read-only server over a `dspack` JSON file (spec versions v0.1 and v0.2, per the README). Tools include `get-component` (props, usage, tokens, accessibility, composition, constraints), `list-components` filterable by lifecycle `status`, `list-antipatterns` filterable by severity including `must-not`, `get-framework-mapping` (import path, install command), `get-theme`, and `get-layout`. The README's worked question for a token is `get-token { category: "color", name: "foreground" }`. This is a published spec and server, not a case study of a product company. — [ds-mcp README](https://github.com/OyaAIProd/ds-mcp)
- Sekura Design MCP (repo `mictsi/SekuraDesignMCP`) publishes a Dockerized server and a self-reported inventory in the README: "55 components · 15 foundations · 15 UX patterns · 9 layout recipes · 120 semantic tokens · 4 themes · 3 densities · 8 target frameworks." Tools include `get_component` (anatomy, variants, sizes, states, props, tokens, dark-mode behavior, accessibility, do/don't), `get_component_code` for `html`, `css`, `react`, `vue`, `svelte`, `angular`, `blazor`, or `web-component`, `suggest_token`, `export_tokens` (CSS, SCSS, W3C DTCG, Tailwind v3/v4, JS, TS, Swift, Android XML, Figma), and `validate_markup`. The inventory numbers are the repo's own claim. — [SekuraDesignMCP](https://github.com/mictsi/SekuraDesignMCP)
- `ds-pilot` (`lyse-labs/ds-pilot`) scans a components directory and a tokens file, exposes `search_components`, `get_component_props`, `list_tokens`, and `get_token`, and installs a `using-ds-pilot` skill or, if skills are unsupported, `CLAUDE.md` instructions "to check for existing components and tokens before writing UI code." Supported components: React (`.tsx`, `.ts`, `.jsx`, `.js`) and Vue/Nuxt. Supported tokens: DTCG JSON, "plain nested JSON (Figma export)," and CSS custom properties. — [ds-pilot](https://github.com/lyse-labs/ds-pilot)
- Basalt's README says tokens live in Git as DTCG 2025.10 JSON and are served at `https://basalt.run/api/mcp` with a bearer key. Tools: `get_token` (example path `color.action.default`), `list_tokens`, `search_tokens`, `get_component` ("usage, variants, a11y notes, code"), `list_components`, icons, `get_theme`, `check_contrast`. The problem statement ("They hardcode `#3B82F6` instead of using `var(--color-action-default)`") is product copy, not a measured study. — [Basalt MCP.md](https://github.com/basalt-run/design-system/blob/main/MCP.md)
- The open repo `gnegreiros-ux/agentic-design-system` publishes a file layout rather than a production postmortem: `AGENTS.md` as "single source of truth for governance," thin `CLAUDE.md` and `GEMINI.md` adapters, DTCG-style `tokens/primitives.json`, `semantic.json`, and `component.json`, a Style Dictionary config, `scripts/audit-tokens.js` ("drift audit: orphans, ghosts, hardcoded values"), and an ESLint config described as "anti-AI-drift lint (hex, arbitrary values)." Its stated rule: "primitives are never used directly in components. Always go through the semantic layer." This is an example repository, not a company case study. — [agentic-design-system](https://github.com/gnegreiros-ux/agentic-design-system)

### Inferences
- The published architectures converge on a catalog the agent must query (component id, legal variants, token path, import) and a separate prose layer that is supposed to stay short because it goes stale. Adobe says this explicitly by retiring a frozen `DESIGN.md` dump in favor of `primer`. Gusto puts the contract in Zod so illegal variants are unrepresentable. Storybook puts it in a manifest generated from stories and docgen.
- Naming is not standardized across systems. Adobe uses kebab-case ids with a separate `displayName`. Figma Code Connect uses the codebase's `componentName` plus a framework `label`. shadcn uses registry names and `@namespace/item`. Agents are expected to copy the name the catalog returns.
- What the agent is forbidden to invent is encoded differently: Gusto uses `.strict()` unions and validated examples; Adobe uses `validate_usage` diagnostics and ranked `suggest_token`; `ds-mcp` uses `must-not` anti-patterns; Storybook's suggested rules say undocumented props are off limits (see the next section). None of these is a model-level guarantee. Claude's own docs say instruction files are context, not enforcement.

### Gaps
- Searches in this pass did not surface engineering posts from Shopify (Polaris), GitHub (Primer), Atlassian, IBM (Carbon), or Salesforce describing an agent-facing design-system architecture. Absence from these searches is not evidence those posts do not exist.
- Adobe's spec is still `1.0.0-draft`, and component authoring is unshipped. The read path for Spectrum tokens and component schemas is the part that is documented as shipped.
- Sekura's component and contrast counts, and Basalt's hallucination anecdote, are self-reported. No independent audit was found.
- Gusto has not published the Workbench schema package or the MCP server source. The architecture is known from the two engineering posts and a conference abstract.

## How do Figma MCP, Cursor, Claude, v0, and similar tools instruct agents to use a design system?

### Takeaway
Official instructions are procedural and negative at the edges: call the design-system tool first, reuse the returned component and token names, treat Figma's React+Tailwind output as a design representation, and do not hardcode values or undocumented props. They are prompt text and tool descriptions. Claude's docs say that text is not an enforcement mechanism.

### Cited Findings
- Figma's documented "General rules" template, to paste into the agent's project rules: "Always use components from `/path_to_your_design_system` when possible"; "Avoid hardcoded values, use design tokens from Figma where available"; "Follow WCAG requirements for accessibility"; "avoid inline styles unless truly necessary." — [Figma Developer Docs, Add custom rules and instructions](https://developers.figma.com/docs/figma-mcp-server/add-custom-rules/)
- Figma's "Rules for consistent output" require this order: (1) `get_design_context` for the exact node; (2) if the response is too large or truncated, `get_metadata`, then `get_design_context` only for the needed nodes; (3) `get_screenshot`; (4) only then download assets and implement; (5) "Translate the output (usually React + Tailwind) into this project's conventions… Reuse the project's color tokens, components, and typography wherever possible"; (6) validate against Figma. Implementation rules say to treat that React+Tailwind as "a representation of design and behavior, not as final code style," to "Replace Tailwind utility classes with the project's preferred utilities/design-system tokens," and to "Reuse existing components (e.g., buttons, inputs, typography, icon wrappers) instead of duplicating functionality." When visual parity and tokens conflict: "prefer design-system tokens and adjust spacing or sizes minimally to match visuals." — [Figma Developer Docs, Add custom rules and instructions](https://developers.figma.com/docs/figma-mcp-server/add-custom-rules/)
- Figma's asset rules, with Cursor and Claude Code placements specified: put them in `.cursor/rules` (Cursor, `alwaysApply: true` in the sample) or `CLAUDE.md` (Claude Code). The sample says: "If the Figma MCP server returns a localhost source for an image or an SVG, use that image or SVG source directly"; "DO NOT import/add new icon packages, all the assets should be in the Figma payload"; "do NOT use or create placeholders if a localhost source is provided." — [Figma Developer Docs, Add custom rules and instructions](https://developers.figma.com/docs/figma-mcp-server/add-custom-rules/)
- Figma documents `search_design_system` as searching connected libraries "so your agent can reuse what already exists instead of creating new elements." `get_design_context` example prompts include "Generate my Figma selection using components from src/components/ui." `get_variable_defs` example prompts include "List the variable names and their values used in my Figma selection." `get_metadata` exists because "`get_design_context` returns too much at once" on very large designs. `get_screenshot` "use[s] more tokens." — [Figma Developer Docs, Tools and prompts](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)
- Code Connect UI instructions are included in the MCP payload "as user rules." The docs tell teams to document "prop patterns, accessibility requirements, and team conventions," to connect core components first, and to "Keep connections up to date" when the code API changes. CLI connections supply the snippets the team wrote, including how Figma properties map to props. UI connections generate a snippet from the Figma component name and current properties, "not full code snippets." — [Figma Developer Docs, Code Connect integration](https://developers.figma.com/docs/figma-mcp-server/code-connect-integration/)
- Storybook's documented `AGENTS.md` starter says: "When working on UI components, always use the `your-project-sb-mcp` MCP tools… before answering or taking any action." Then: "CRITICAL: Never hallucinate component properties! Before using ANY property on a component from a design system (including common-sounding ones like `shadow`, etc.), you MUST use the MCP tools to check if the property is actually documented." The required sequence is `docs-list`, then `docs-show`, then "Only use properties that are explicitly documented or shown in example stories." "If a property isn't documented, do not assume properties based on naming conventions or common patterns from other libraries. Check back with the user." Also: call `get-storybook-story-instructions`, and "Check your work by running `test-run`." `docs-show` returns props, the first three stories, an index of the remaining stories, and extra docs. — [Storybook docs, MCP server](https://storybook.js.org/docs/ai/mcp/overview)
- shadcn's official docs do not ship a design-system rules paragraph. They show prompts such as "Build a landing page using components from the acme registry" and "Create a contact form using components from the shadcn registry," and they say registries are configured in `components.json`. A third-party writeup (Wingo UI) claims that, as the author observed in Cursor, the server is read-only, "sends no instructions," and `view_items_in_registries` returned no props, so "that is the rule's job." That tool list was not re-verified here. Treat it as one implementer's report. — [shadcn/ui, MCP Server](https://ui.shadcn.com/docs/mcp); [Wingo UI, Cursor shadcn Setup](https://wingo-ui.com/blog/cursor-shadcn-mcp-rules)
- v0's Design Systems 2.0 docs: "v0 grounds itself in the real source. If a component, prop, or token cannot be verified from the sources, v0 should not use it." Notes are the place for "Deprecated components, anti-patterns, or gotchas" and "Component conventions v0 should prefer or avoid." Passing the skill in the API `skills` field "loads it for that request instead of asking the agent to decide whether it is relevant." Mentioning the design system in the message does not force the skill to load. — [v0, Design Systems 2.0](https://v0.app/docs/design-systems-2); [v0 API, Design Systems](https://v0.app/docs/api/v2/guides/design-systems)
- Claude Code docs, operational rather than design-system-specific: instructions are context, not configuration; "The more specific and concise your instructions, the more consistently Claude follows them"; target under 200 lines; contradictory instructions mean "Claude may pick one arbitrarily"; `/doctor prompt-audit` looks for instructions written for older models, references to missing files, and files that contradict each other. A design-system rule in `CLAUDE.md` is therefore a hint, unless the team also adds a hook. — [Anthropic, How Claude remembers your project](https://code.claude.com/docs/en/memory)
- Gusto's stated model instruction, from the engineering post: "We pair that publication with a short prompt telling the model the right discipline: copy from .meta().examples. Don't invent." — [Jay Johnson, Part 1, 27 July 2026](https://engineering.gusto.com/eval-driven-design-systems-8f781dc2dacb)
- A vendor template (UIX "AI Pack"), not a company postmortem, puts these lines in `AGENTS.md`: "Never hard-code colors, font sizes, spacing, radii, shadows or durations"; "Semantic over primitive: `bg-surface`, `text-fg-primary`, `border-line-default`, not `blue-500` or `#2563eb`"; "Reuse before you build: check design-system/components.json first"; required states hover, active/pressed, focus-visible, disabled, and input error; "WCAG 2.2 AA"; "Dark mode: tokens switch with `data-theme` on `<html>`. Never write separate dark colors." The same pack ships DTCG JSON under `tokens/*.tokens.json` and a `components.json` catalog of "exact variant values." Useful as an example of the rule style teams are copying, not as evidence of production results. — [UIX, AGENTS.md, DESIGN.md and the AI Pack](https://useuix.com/docs/ai-pack)

### Inferences
- The operational rule repeated across Figma, Storybook, v0, and Gusto is: the catalog is closed. Names, props, variants, imports, and token paths come from a tool or schema response. The model does not extend the system inside a generation.
- Figma's own default codegen (React + Tailwind) is documented as an intermediate representation. The project rule is what maps it onto design-system tokens. Without that rule, the documented output is utility classes, not the team's token names.
- Cursor does not appear, in the official Figma or shadcn pages, to have a design-system-specific product mode. The integration path those docs give Cursor is `.cursor/mcp.json` plus `.cursor/rules`. Claude's path is `.mcp.json` plus `CLAUDE.md` or `AGENTS.md`.

### Gaps
- Cursor's own documentation for rule-file format was not fetched. Placement of Figma rules in `.cursor/rules` is Figma's instruction. Claims about `.mdc` frontmatter, `alwaysApply`, and globs come from the third-party Wingo post and Figma's sample, not from a Cursor docs page read in this pass.
- The exact XML tag Figma wraps Code Connect snippets in was stripped out of the fetched HTML. The fields inside the marker are cited above; the tag name is not.
- No official Cursor, Claude, or v0 page was found that quotes a rule of the form "map Figma variables to code tokens" in those words. The closest official wording is Figma's "use design tokens from Figma where available" and "Replace Tailwind utility classes with the project's preferred utilities/design-system tokens."
- v0 docs do not publish the generated skill text, so the precise sentences v0 injects per customer are not public.

## What breaks in practice?

### Takeaway
The failures that named authors and official docs describe are invented components and props, illegal enum values, wrong import paths, hardcoded colors, stale prose or Code Connect mappings, context limits on large Figma nodes and large catalogs, and accessibility or content mistakes that still compile. Drift between Figma and code is treated as an expected maintenance problem (update Code Connect, diff datasets, do not trust a frozen prose dump), not as a solved sync.

### Cited Findings
- Gusto's part 2, 3 August 2026, shows a prop the schema does not have: the model wrote `<Button variant="primary" intent="submit">` and the fix is `<Button variant="primary">`. Johnson writes: "intent doesn't exist on the schema." He also names `variant="large"` as "a common failure mode that prop-validity misses because the prop exists, but the value is invalid." A separate failure both compiles and scores perfectly on the mechanical checks: prompt "add a button to confirm and continue the payroll submission" produced "Confirm and continue"; the content guideline is "one verb per button, three words max." He says failure categories "are the same now as they were six months ago, just less frequent," and that "Aggregate scores swing around based on model versions, dataset additions, and schema revisions." Part 1 says models invented imports "from `@gusto/design-system/button` when no such submodule exists," and that publishing the exact `importStatement` "killed an entire category of hallucinations on its own." — [Jay Johnson, Part 1, 27 July 2026](https://engineering.gusto.com/eval-driven-design-systems-8f781dc2dacb); [Part 2, 3 August 2026](https://engineering.gusto.com/eval-driven-design-systems-part-2-5b989d492281)
- `open-design-system-bench` documents hallucinations found against a system it calls Aurora: the system has a `heading` prop and the model invented a `Heading` component; the system has `Text` and the model used `Typography`; the model invented spacing props on Box and Card. The README quotes a handoff failure: "we don't really have any of these props, or this is an invented component." The bench treats a hallucinated component as a hard fail. — [open-design-system-bench](https://github.com/christophhdesign/open-design-system-bench); summary of the Aurora cases also in [Into Design Systems, How to Measure If AI Agents Actually Use Your Design System](https://intodesignsystems.substack.com/p/how-to-measure-if-ai-agents-actually)
- Cristian Morales, writing about running that bench on his own system, reports that prose files (`AGENT.md`, `llms.txt`, skills) "can produce poor quality output by providing stale instructions" and that "stale, duplicated, or authoritative-looking information can conflict with the source of truth." He reports bare runs, without those files, scoring higher when the files hardcoded a component or token list, including "ghost tokens" from an earlier agent run. After deleting about 90% of `AGENT.md`, a 90-cell run scored 72; restoring a pointer to the generated contract plus a validation gate returned the score to 90 with "around 41%" lower token cost. He also reports a case that scored 100 on mechanical checks and 26 on judgment. These figures are one author's measurements of his own system, not a multi-team study. — [Cristian Morales, What does AI-Readiness mean in Design Systems?](https://www.giorris.dev/thoughts/what-does-ai-readiness-mean-in-design-systems)
- Storybook's own docs lead with the failure mode the tools are aimed at: agents "make up" component properties, including "common-sounding ones like `shadow`." The suggested login-form workflow includes the agent discovering, via `test-run`, that a submit button "does not have an accessible level of color contrast," then picking a documented theme color and re-running. That is a documented scenario, not a published failure rate. `docs-show` only inlines the first three stories, so variants that exist only in later stories are invisible unless the agent calls `docs-show-story`. — [Storybook docs, MCP server](https://storybook.js.org/docs/ai/mcp/overview); [Kyle Gach, 23 March 2026](https://storybook.js.org/blog/storybook-mcp-for-react/)
- Figma documents two truncation paths: `get_design_context` "returns too much at once" on large selections, and screenshots "use more tokens." The rules tell the agent to refetch subsets via `get_metadata`. The same rules say the default React+Tailwind output is not the project's code style, which is the documented path by which a generation hardcodes Tailwind utilities instead of team tokens. Code Connect's best-practices section says mappings go stale when "a component's API changes" unless someone updates the connection. On Professional plans, only the active library and framework's connections are returned, so an agent can miss a mapping that exists for another framework. — [Figma Developer Docs, Tools and prompts](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/); [Add custom rules](https://developers.figma.com/docs/figma-mcp-server/add-custom-rules/); [Code Connect integration](https://developers.figma.com/docs/figma-mcp-server/code-connect-integration/)
- Adobe says a frozen prose summary drifts, which is why `primer` replaced "DESIGN.md emit." Spectrum guidelines shipped inside the MCP package "may lag" the public site. The embedded dataset updates only when the package is upgraded, not live. `validate_usage` and `diff_datasets` exist to catch token misuse and dataset drift. The worked example still has the agent "emit CSS using that value," so a literal resolved color can leave the token path if the consumer does not keep the token name. — [Adobe, Agent-readable surface](https://opensource.adobe.com/spectrum-design-data/spec/agent-surface/); [Adobe, Using AI](https://opensource.adobe.com/spectrum-design-data/ai/)
- Murphy Trueman's essay "Design systems need evals" describes failures that code review misses: a model update changes how tokens are used while `AGENTS.md` stays untouched, and "Someone trims three lines out of AGENTS.md… and silently breaks a behaviour nobody re-tests." He separates mechanical failures (invented prop, raw hex, hand-rolled markup, confirmation dialog with no accessible name) from judgment failures (wrong component for the intent, missing empty and error states). No dataset is attached. — [Murphy Trueman, Design systems need evals](https://blog.murphytrueman.com/design-systems-need-evals/)
- Claude Code's memory docs state a general adherence failure: long instruction files "reduce adherence," and contradictory instructions can be resolved by picking one arbitrarily. Auto memory is capped at the first 200 lines or 25KB, so anything past that cap is not in context. — [Anthropic, How Claude remembers your project](https://code.claude.com/docs/en/memory)
- Storybook's Kyle Gach post says a Reshaped benchmark compared generating UI with and without Storybook MCP and that MCP was "faster and with fewer tokens." The numeric table is an image in the post and was not extracted. No figures are cited here. — [Kyle Gach, Storybook MCP for React, 23 March 2026](https://storybook.js.org/blog/storybook-mcp-for-react/)

### Inferences
- "Invented component" and "invented prop" are the failures with the most concrete public examples (Gusto `intent`, Aurora `Heading` / `Typography` / spacing props, Storybook's `shadow` warning). Token misuse is widely warned about and is a scored dimension in the open bench, but the public writeups show fewer verbatim before/after diffs for raw hex than for bad props.
- Undocumented variants fail in two directions: the agent invents a variant the schema does not have (`variant="large"`), or a real variant exists only in a story/index the agent did not fetch (`docs-show` inlines three stories). Gusto's response to the first is to make the illegal combination unrepresentable in the schema, not to write a longer prompt.
- Context-window limits are handled by pagination in the official tools (Figma `get_metadata` then subset refetch; Storybook list → show → show-story; Adobe 2,000-token primer) rather than by putting the whole system in the prompt. The failure mode when teams ignore that is stale or truncated prose, which Morales and Adobe both describe as a source of further invention.
- Accessibility regressions show up as a separate loop (Storybook `test-run`, contrast tools on Basalt and Sekura, Gusto `accessibilityGuidelines`) because prop-validity does not catch a button that is on-schema and unlabeled or low-contrast.

### Gaps
- No public measurement of Figma-versus-code drift rates (how often Code Connect mappings are wrong, how often variables and code tokens disagree). The sources describe the maintenance task and the tools (`diff_datasets`, Code Connect updates), not a rate.
- Storybook's Reshaped benchmark numbers were not readable from the fetched text.
- Basalt's hex-versus-CSS-variable example is marketing copy. It matches the failure mode other sources describe, but it is not evidence of a measured incident.
- This pass did not find a published incident report from a product team quantifying accessibility regressions caused by an agent.

## What metrics or evals do teams use?

### Takeaway
There is no shared industry metric. The public eval designs that exist are Gusto's Braintrust scorers on Workbench, the open-source `open-design-system-bench` harness, and Storybook's in-loop `test-run` (interaction and accessibility on stories the agent wrote). All of them split a mechanical gate (legal component, prop, enum, import, token, compile) from a judgment score (right component and content for the intent). Gusto is explicit that aggregate scores move for reasons that are not product quality.

### Cited Findings
- Gusto part 2: 167 hand-written prompts across 25 components, plus a second dataset of real engineer requests. The model receives the schema and `.meta()` and returns JSX. Three deterministic scorers: `prop-validity` (fractional; unknown tags count as hallucinations; one invented prop gets partial credit), `enum-validity` (legal enum value), `import-match` (import string equals the schema). Human ratings on two further axes: intent ("did the model solve the problem?") and idiom ("is this how a fluent author would write it?"). Rationales are kept "to seed our future LLM-as-judge scorers." Production instrumentation stores the verbatim request, groups tool calls that belong to one request, and a periodic job turns that into eval rows with no golden JSX, because the scorers compare against the schema. Johnson's recommended minimum: five components, a schema with prop types, three validated examples, and the exact import; ten plain-English prompts each; at least `prop-validity`; rerun when schemas change. The suite runs on Braintrust. He does not publish the numeric aggregate. — [Jay Johnson, Part 2, 3 August 2026](https://engineering.gusto.com/eval-driven-design-systems-part-2-5b989d492281); setup in [Part 1, 27 July 2026](https://engineering.gusto.com/eval-driven-design-systems-8f781dc2dacb)
- `open-design-system-bench` (author repo `christophhdesign`, methodology credited to "Design Systems Need Evals") runs intent-level prompts that "never name the expected component." Default is 3 runs per task per model, "The worst run counts." Dimensions and weights from the README: imports 0.10 (only the system package, React, and local files; a foreign UI library is review/fail), apiFidelity 0.25 (imports must be a subset of the extracted catalog; no invented props; hallucinated component is a hard fail), tokenDiscipline 0.15 (no raw hex/rgb, no arbitrary Tailwind such as `bg-[#…]` or `w-[137px]`, no hardcoded inline-style colors, no raw values in CSS/SCSS), a11yStatic 0.10 (accessible names, img alt, positive tabindex, click-without-key, label association, valid `aria-*`, autofocus, anchor validity), compile 0.10 (`tsc --noEmit`; an error in the agent's files fails), judgment 0.30 (per-task rubric, separate model, default `claude -p` with Haiku, blind to cell config; a critical rubric fail is review). Catalogs are extracted with react-docgen-typescript, a prebuilt catalog JSON, or Stencil `docs.json`, and "extraction refuses a stale one." A judge rationale that claims a component is used is checked against the diff; a contradicted claim caps the cell at review. — [open-design-system-bench](https://github.com/christophhdesign/open-design-system-bench)
- Morales's writeup is a single-system use of that bench: scores he reports are 90, then 72, then 90 on a "high profile (90 cells)" run, and a judgment score of 26 alongside a mechanical 100. He treats generated instruction files as something the bench should be allowed to falsify. — [Cristian Morales](https://www.giorris.dev/thoughts/what-does-ai-readiness-mean-in-design-systems)
- Trueman describes the same two-layer eval (mechanical checks against the real API and token set; an LLM judge for component choice and empty/error states) and argues for running it in CI because model updates and edits to `AGENTS.md` change behavior without a code review catching it. He names promptfoo, "acquired by OpenAI in March," as the tool that made these checks cheap. He does not publish a suite. — [Murphy Trueman, Design systems need evals](https://blog.murphytrueman.com/design-systems-need-evals/)
- Storybook's `test-run` "runs tests for specific stories and returns results, including any accessibility issues (if configured)" and "instructs the agent to interpret the results and resolve any issues found." That is an in-loop check on stories, not a cross-model benchmark of design-system fidelity. The Gach post says the agent "only tests what it deems relevant." — [Storybook docs, MCP server](https://storybook.js.org/docs/ai/mcp/overview); [Kyle Gach, 23 March 2026](https://storybook.js.org/blog/storybook-mcp-for-react/)
- Adobe's `validate_usage` returns a `ValidationReport` whose diagnostics must include `rule_id`, `severity`, `message`, `instance_path`, `schema_path`, `file`, and `token` where applicable. `diff_datasets` returns a semantic diff. These are validators on design data, not a published score for generated UI. — [Adobe, Agent-readable surface](https://opensource.adobe.com/spectrum-design-data/spec/agent-surface/)
- Sekura exposes `check_contrast`, `audit_theme` ("Every declared pairing across every theme. The build gate."), and `validate_markup`. The README's "344 contrast checks" and "0 axe violations" are the project's own inventory, not an agent-fidelity eval. — [SekuraDesignMCP](https://github.com/mictsi/SekuraDesignMCP)
- The example repo `agentic-design-system` ships `scripts/audit-tokens.js` for orphans, ghosts, and hardcoded values, and an ESLint config aimed at hex and arbitrary values. That audits the codebase, not an agent's completion. — [agentic-design-system](https://github.com/gnegreiros-ux/agentic-design-system)

### Inferences
- Where a number exists, it is a rubric over generated code, not a product KPI. The dimensions that more than one source scores are: legal component identity, legal props, legal enum values, exact imports, absence of raw color and spacing, static accessibility, and a separate judgment of whether the choice matched the intent.
- Hard gates in the open bench (hallucinated component fails; compile error fails) are stricter than Gusto's fractional `prop-validity`. A team copying "the metric" has to choose which of those contracts it means.
- Storybook's self-healing `test-run` can catch contrast and interaction bugs in stories the agent wrote. It does not, on the evidence here, know whether the agent should have used a different component.

### Gaps
- Gusto does not publish the aggregate scores, the model names, or the pass rates. The FITC abstract does not add numbers.
- No second product company was found publishing a comparable eval suite. Adobe publishes validators, not generation scores.
- No standard threshold (for example, a minimum api-fidelity score before an agent is allowed to open a pull request) appears in the official Figma, Storybook, shadcn, v0, or Claude docs.
- promptfoo's acquisition claim is Trueman's, and was not checked against an OpenAI announcement in this pass.

# Agentic ဒီဇိုင်းစနစ်ကို စစ်ဆေးနိုင်အောင် တည်ဆောက်ပါ

၂၀၂၆ ခုနှစ် နိုဝင်ဘာ ၂၁ ရက်အထိ အများပြည်သူရင်းမြစ်များက **agentic design system** ကို အရာဝတ္ထုတစ်ခုတည်းအဖြစ် မသတ်မှတ်ရသေးပါ။ စကားလုံးသည် အနည်းဆုံး အဓိပ္ပာယ်သုံးခုကို ရောညွှန်းနေသည်။ ပထမအဓိပ္ပာယ်မှာ လူသားဒီဇိုင်းစနစ်ကို agent က ဖတ်နိုင်၊ အသုံးချနိုင်၊ မော်ဒယ်အပြင်ဘက်မှ မှားကြောင်း ပြောနိုင်အောင် token၊ component စာချုပ်၊ အသုံးပြုပုံစည်းမျဉ်းတို့ဖြင့် ပြင်ဆင်ထားခြင်းဖြစ်သည်။ ဒုတိယအဓိပ္ပာယ်မှာ agent ပါသော ထုတ်ကုန်၏ UX ပုံစံစာကြည့်တိုက်ဖြစ်သည်။ တတိယအဓိပ္ပာယ်မှာ agent ကိုယ်တိုင်က စာရွက်၊ token၊ pull request ကို လူတစ်ဦး၏ ခွင့်ပြုချက်အောက်တွင် ရေးခြင်းဖြစ်သည်။ လက်ရှိ အများပြည်သူစနစ်များ ပြီးစီးခါနီးအပိုင်းမှာ token နှင့် typed API ဖြစ်ပြီး၊ agent အတွက် စာရွက်စာတမ်းနှင့် ထုတ်ကုန်အဖွဲ့သို့ ဦးတည်သော လမ်းညွှန်မှာ လစ်ဟာနေသည်။ Supernova က ၂၀၂၆ အောက်တိုဘာ ၅–၆ တွင် စနစ် ၃၁ ခုကို ၁၀ မှတ်ဖြင့် စစ်ဆေးရာ **median ၅ မှတ်** ရပြီး၊ ပျောက်နေသော ၁၄၈ မှတ်အနက် **၁၃၅ မှတ်** သည် agent ဝင်ရောက်မှု၊ စာရွက်စာတမ်း၊ လမ်းညွှန်ဘက်တွင် ရှိသည် ([How AI-Ready Are Design Systems?](https://www.supernova.io/blog/ai-ready-design-systems-2026-study))။ တည်ဆောက်သင့်သော အစီအစဉ်ကို ရင်းမြစ်များက အခြေအနေနှစ်မျိုးဖြင့် ခွဲသည်။ အခြေခံအားနည်းလျှင် အမည်ပေးခြင်း၊ semantic token၊ component စာချုပ်ကို အရင် ရေးသည်။ token နှင့် API ပြည့်ပြီးလျှင် consumer `AGENTS.md` နှင့် `llms.txt` ကို အရင် ထုတ်ပြီး MCP ကို အစပိုင်းတွင် ဖတ်ခွင့်သီးသန့်ထားသည်။ မော်ဒယ်က ကိုယ့်အထွက်ကို ကိုယ်ပြန်သဘောတူခြင်းကို evaluation အဖြစ် မရေတွက်ရ။ API အသစ်၊ breaking change၊ governance ဆုံးဖြတ်ချက်ကို agent က ပိုင်ရှင်မဖြစ်စေရ။

## စကားလုံးတစ်လုံးက အရာဝတ္ထုသုံးမျိုးကို ရောခေါ်နေသည်

၂၀၂၄ မှ ၂၀၂၆ နိုဝင်ဘာအတွင်း ဤစကားစုကို ဘယ်သူ အရင် ရိုက်နှိပ်ခဲ့သည်ကို ဤမှတ်စုများက မသတ်မှတ်နိုင်ပါ။ ရက်စွဲပါသော အစောဆုံး လူသိများမှုသည် ယန္တရားဘက်တွင် Figma ၏ Schema 2025 ပြန်လည်သုံးသပ်ချက် (၂၀၂၅ အောက်တိုဘာ ၂၈၊ Paige Costello) ဖြစ်ပြီး၊ ခေါင်းစဉ်ထဲက စကားစုဘက်တွင် Brad Frost နှင့် Chromatic ဆွေးနွေးပွဲ (အညွှန်းစာမျက်နှာများက ၂၀၂၅ ဒီဇင်ဘာ ၁၁ ဟု မှတ်သည်) နှင့် Frost ၏ ၂၀၂၅ ဒီဇင်ဘာ ၁၆ ဆောင်းပါးဖြစ်သည်။ Anthropic၊ Microsoft Fluent၊ Adobe Spectrum၊ Google Material တို့က ဤစကားစု၏ အဓိပ္ပာယ်ဖွင့်ဆိုချက်ကို ဤရှာဖွေမှုတွင် မထုတ်ပြန်ထားပါ။ ထို့ကြောင့် အသေးစားအဖွဲ့တစ်ဖွဲ့သည် စကားလုံးကို အရင် ခွဲပြီးမှ အလုပ်စရမည်။

| --- | --- | --- |
| Meaning A | agent ဖတ်၊ အသုံးချ၊ ပြင်ပမှ စစ်နိုင်သော လူသားဒီဇိုင်းစနစ် | Aestheria၊ Into Design Systems၊ Figma၊ Brad Frost |
| Meaning B | agent ထုတ်ကုန်၏ UX ပုံစံ၊ ထုတ်ဖော်မှု၊ ပြန်ပြင်မှု | Shape of AI၊ RAD၊ NN/g ၏ agent UX ဆောင်းပါးများ |

Meaning A သည် ၂၀၂၅ နှောင်းပိုင်းမှ ၂၀၂၆ နိုဝင်ဘာအထိ ဒီဇိုင်းစနစ်ရောင်းချသူများနှင့် ဒီဇိုင်းစနစ်ဦးဆောင်သူများကြား လွှမ်းမိုးသော အများပြည်သူသုံးနည်းဖြစ်သည်။ Aestheria က ၂၀၂၆ ဩဂုတ် ကွင်းဆင်းမှတ်တမ်းတွင် ဤသို့ ရေးသည်။ agentic design system ဆိုသည်မှာ agent က ထုတ်ကုန် UI တည်ဆောက်သောအခါ ဖတ်နိုင်၊ အသုံးချနိုင်၊ စစ်ဆေးခံနိုင်သော ဒီဇိုင်းစနစ်ဖြစ်ပြီး၊ token၊ ကန့်သတ်ချက်၊ component စာချုပ်၊ အသုံးပြုပုံစည်းမျဉ်းကို စာပိုဒ်စာရွက်အဖြစ် မထားဘဲ စက်ဖတ်နိုင်သော context အဖြစ် ထည့်သွင်းထားသည်။ ခွဲခြားသော လက္ခဏာမှာ agent က ထုတ်လုပ်နိုင်ခြင်းမဟုတ်ပါ။ စနစ်က အထွက်မှန်မမှန် ဆုံးဖြတ်နိုင်ခြင်းဖြစ်သည်။ MCP သည် ပို့ဆောင်နည်းတစ်ခုဖြစ်ပြီး လိုအပ်ချက်မဟုတ်ပါ ([What is an agentic design system?](https://aestheria.design/blog/what-is-an-agentic-design-system))။ Into Design Systems ၏ ၂၀၂၆ ညီလာခံအနှစ်ချုပ်က အလားတူ အခြေခံအဆောက်အအုံအဓိပ္ပာယ်ကို ပေးသည်။ ရည်ရွယ်ချက်၊ ဆက်နွယ်မှု၊ ကန့်သတ်ချက်ကို စက်ဖတ်နိုင်အောင် ရေးထားသော စနစ်ဖြစ်သည် ([Agentic Design Systems: The Complete Guide](https://www.intodesignsystems.com/agentic-design-systems))။ Figma က ၎င်း၏ စာမျက်နှာတွင် “LLM context design” ဟု ခေါ်ပြီး၊ မော်ဒယ်က ယုံကြည်စွာ ဖတ်နိုင် အသုံးချနိုင်သော ပုံစံဖြင့် ဒီဇိုင်းစနစ်ကို ရေးခြင်းဟု ဆိုသည်။ အလွှာသုံးခုမှာ token၊ အသုံးပြုပုံစည်းမျဉ်းပါ spec၊ စစ်ဆေးလှည့်ပတ်မှုဖြစ်ပြီး၊ tool access ကို Figma MCP နှင့် ချိတ်သည် ([LLM Context Design](https://www.figma.com/resource-library/llm-context-design/))။ Brad Frost သည် ၂၀၂၅ ဒီဇင်ဘာ ၁၆ တွင် စကားစုကို သူတီထွင်ခဲ့သည်ဟု မဆိုပါ။ သူသုံးသော အတိုကောက်မှာ **DS+AI** ဖြစ်သည်။ Storybook MCP ဖြင့် ခိုင်မာပြီးသား component စာကြည့်တိုက်ထဲက ပစ္စည်းများကို သုံးကန့်သတ်ထားသော ထုတ်လုပ်မှုသည် vibe coding နှင့် ကွဲသည်ဟု ရေးသည် ([Agentic Design Systems in 2026](https://bradfrost.com/blog/post/agentic-design-systems-in-2026/))။

Meaning B သည် လက်တွေ့အလေ့အကျင့်အနေဖြင့် ပိုစောပြီး၊ စကားစုကိုယ်တိုင်ကို ရှားရှားပါးပါး သုံးသည်။ Emily Campbell ၏ Shape of AI သည် “UX of AI” အတွက် အများပြည်သူပုံစံစာကြည့်တိုက်ဖြစ်ပြီး Wayfinders၊ Prompt actions၊ Tuners၊ Governors၊ Identifiers ဟု အုပ်စုဖွဲ့သည်။ Governors တွင် Action plan၊ Stream of Thought၊ Verification၊ Citations၊ Cost estimates ပါသည်။ about စာမျက်နှာက “agentic design system” ကို မသုံးပါ ([The Shape of AI](https://www.shapeof.ai/))။ Campbell က ၂၀၂၆ ဇွန် ၄ တွင် “Agentic UX” ကို သီးခြားစည်းကမ်းတစ်ခုအဖြစ် ရေးပြီး၊ agent ကို ကျွမ်းကျင်မှု၊ tool၊ ဒေတာကို ပန်းတိုင်တစ်ခုသို့ ချိန်ထားသော ကိုယ်ပိုင်စနစ်ဟု ဖွင့်သည်။ အလွှာများမှာ User interfaces၊ Context၊ Harness၊ Model၊ Governance၊ Emergence ဖြစ်သည် ([Designing beneath the surface](https://shapeofai.substack.com/p/designing-beneath-the-surface-the))။ ဤပုံစံစာကြည့်တိုက်ကို “design system” ဟု ခေါ်သော ရှင်းလင်းသည့် ဥပမာမှာ RAD ဖြစ်သည်။ GitHub Pages လမ်းကြောင်း `jackiecurry` အောက်တွင် Responsible, Accountable, Disclosed ပုံစံများ၊ Agent Activity Timeline၊ Human Approval Gate၊ Tool Execution Log၊ Source Trace၊ Confidence Display၊ Agent State Indicator တို့ကို “ဒီဇိုင်းစာချုပ်” ဟု ရေးသည်။ ရေးသူအမည်နှင့် ရက်စွဲကို ထိုစာမျက်နှာက မပေးပါ ([RAD](https://jackiecurry.github.io/rad/))။

Meaning C သည် ထုတ်ကုန်စာသားထဲတွင် ရှိပြီး၊ အများအားဖြင့် ခွင့်ပြုချက်ပါသော ပြန်ရေးခြင်းဖြစ်သည်။ zeroheight MCP က စာရွက်စာတမ်းကို agent ဖြင့် ထိန်းသိမ်းနိုင်သည်ဟု ရေးပြီး၊ MCP-Write ကို editor နှင့် admin သာ သုံးနိုင်သည် ([zeroheight MCP](https://zeroheight.com/mcp/))။ Supernova က MCP ပြောနိုင်လျှင် စနစ်ကို ဖတ်နိုင်၊ ပြန်ရေးနိုင်သည်ဟု ဈေးကွက်တင်ပြီး၊ ဥပမာ skill များက အသုံးပြုသူအတည်ပြုပြီးမှ မထုတ်ဝေရသေးသော စာမျက်နှာကို ရေးသည်၊ ကိုယ်တိုင် မထုတ်ဝေဟု ကန့်သတ်ထားသည် ([MCP for design systems](https://www.supernova.io/mcp))။ Into Design Systems က Romina Kavcic ၏ “self-healing loop” (observe, detect, suggest, fix, learn) နှင့် အဆင့်လိုက် ယုံကြည်မှုကို ညီလာခံအနှစ်ချုပ်အဖြစ် ဖော်ပြသည်။ GitHub ၏ Jan Six အကြောင်း အနှစ်ချုပ်တွင်မူ agent ၏ ဘေးကင်းသော အထွက်မှာ issue ဖွင့်ခြင်းသာဖြစ်ပြီး ကုဒ်ကို merge မလုပ်ဟု ပါသည်။ ဤစာကြောင်းများသည် မှတ်တမ်းဖိုင်ကို ပြန်စစ်ထားသော ကိုးကားချက်များမဟုတ်ပါ ([Agentic Design Systems: The Complete Guide](https://www.intodesignsystems.com/agentic-design-systems))။

Aestheria က Meaning A အတွင်း ထပ်ခွဲသည်။ traditional၊ computational၊ generative၊ agentic တို့ကို အဆင့်ဆင့် အစားထိုးမှုအဖြစ် ပယ်ပြီး အထပ်လိုက် မှီခိုမှုအဖြစ် ရေးသည်။ ပိုင်ဆိုင်မှု၊ ထို့နောက် စည်းမျဉ်း၊ ထို့နောက် generation၊ ထို့နောက် agency ဖြစ်သည်။ စည်းမျဉ်းအလွှာမရှိသော agent သည် ပိုမိုအဆင့်မြင့်သော ဒီဇိုင်းစနစ်ဖြစ်လာသည်ဟု ထိုစာက လက်မခံပါ။ ၂၀၂၆ ဩဂုတ်အထိ agentic ကော်လံတွင် **မဖြေရှင်းရသေး** ဟု မှတ်ထားသော အကွက်သုံးခုမှာ လုပ်ဆောင်နေစဉ် ဆုံးဖြတ်ချက်တစ်ခုကို ရှင်းပြခြင်း၊ ထုတ်ထားသော ထုတ်ကုန်တွင် ဘာနှင့် တိုက်ဆိုင်စစ်သလဲ၊ မှားသောအခါ ပြန်လည်ကုစားလမ်းကြောင်း ဖြစ်သည် ([Aestheria](https://aestheria.design/blog/what-is-an-agentic-design-system))။ ရောင်းချသူများက ဖတ်ခွင့်သီးသန့် MCP ကို agentic သို့မဟုတ် agent-ready ဟု ခေါ်နိုင်သည်။ Aestheria က ထိုအရာသည် အောက်ခံအလွှာများသာဖြစ်ပြီး စစ်ဆေးမှုနှင့် ကုစားမှု မပြီးသေးဟု ဆိုသည်။ ဤနှစ်ဘက်စလုံးကို မှတ်စုများက တစ်ခုတည်းသို့ ချေမှုန်းမထားပါ။

ကပ်လျက်အကြောင်းအရာကို ဒီဇိုင်းစနစ်အလုပ်နှင့် ရောရန် NN/g က နေရာမပေးပါ။ Sarah Gibbons နှင့် Kate Moran ၏ ၂၀၂၆ ဧပြီ ၁၀ ဆောင်းပါး “AI Agents as Users” က အသုံးပြုသူသည် လူသားနှင့် တူညီတော့မည်မဟုတ်ကြောင်း၊ agent များက ဝဘ်ဆိုက်သွား၊ ဖောင်ဖြည့်၊ နှိုင်းယှဉ်၊ ငွေလွှဲနိုင်ကြောင်း ရေးသည်။ အပြန်အလှန်နည်းသုံးမျိုးမှာ screenshot၊ accessibility tree၊ API သို့မဟုတ် MCP ဖြစ်သည်။ ထိုဆောင်းပါး၏ ဒီဇိုင်းအကြံမှာ ထုတ်ကုန်ကို agent လည်ပတ်နိုင်အောင် accessibility နှင့် ခန့်မှန်းနိုင်သော ပုံစံများထားရန်ဖြစ်ပြီး၊ ဒီဇိုင်းစနစ်အခြေခံအဆောက်အအုံအကြောင်း မဟုတ်ပါ။ agent အတွက် အကောင်းဆုံးမလုပ်သင့်သော အကြောင်းများ (လာရောက်မှုကိုယ်တိုင်က ထုတ်ကုန်ဖြစ်ခြင်း၊ ရည်ရွယ်ချက်ရှိသော ပွတ်တိုက်မှု၊ ပြိုင်ဆိုင်ဒေတာ) ကိုလည်း စာရင်းပြုသည် ([AI Agents as Users](https://www.nngroup.com/articles/ai-agents-as-users/))။

အဓိပ္ပာယ်ဖွင့်ဆောင်းပါးများက တူညီသော အချက်တစ်ခုတွင် ဆုံသည်။ agent အတွက် လိုအပ်သည်မှာ ၎င်းက ကြံဆဖြည့်၍ မကျေနပ်နိုင်သော ကန့်သတ်ချက်ဖြစ်သည်။ စာချုပ်၊ အသုံးပြုပုံစည်းမျဉ်း၊ စမ်းသပ်ချက်၊ သို့မဟုတ် လူ့တံခါး ဖြစ်နိုင်သည်။ “MCP တင်လိုက်ရုံ” နှင့် “token ထုတ်လိုက်ရုံ” နှစ်ခုစလုံးသည် Aestheria၊ Into Design Systems၊ Figma ၏ LLM-context စာမျက်နှာ၊ Frost တို့၏ အဓိပ္ပာယ်ဖွင့်ချက်ထဲတွင် လျော့နည်းသော ရပ်တည်ချက်ဖြစ်သည်။ Meaning A နှင့် Meaning B ကို ရင်းမြစ်များက အချင်းချင်း ကိုးကားခဲသည်။ Shape of AI က Figma MCP ကို မကိုးကားပါ။ Figma ၏ LLM-context စာမျက်နှာက Shape of AI သို့မဟုတ် RAD ကို မကိုးကားပါ။

## အများပြည်သူစနစ် ၃၁ ခု၏ median သည် ၅/၁၀ တွင် ရပ်နေသည်

တရားဝင်စာရွက်များနှင့် အများပြည်သူအကောင်အထည်ဖော်မှုများ ထပ်နေသော အထပ်မှာ ဤသို့ဖြစ်သည်။ token အတွက် **Design Tokens 2025.10** (၂၀၂၅ အောက်တိုဘာ ၂၈ တွင် ပထမဆုံး တည်ငြိမ်ဗားရှင်း၊ Format၊ Color၊ Resolver မော်ဂျူးသုံးခု၊ W3C Standard မဟုတ်သော Final Community Group Report)၊ Style Dictionary ကဲ့သို့သော build အဆင့်၊ agent က မေးရမည့် component catalog၊ ထိုကိရိယာများကို ညွှန်သော စည်းမျဉ်းဖိုင်တို (`AGENTS.md`၊ `CLAUDE.md`၊ သို့မဟုတ် Cursor rules) ဖြစ်သည်။ ဤပေါင်းစပ်မှုကို အဖွဲ့အများစု သုံးသည်ဟု တိုင်းတာသော စစ်တမ်းမရှိပါ။ “လက်ရှိ ပုံစံ” သည် စာရွက်များ ထပ်နေခြင်းမှ ကောက်ချက်ဖြစ်သည် ([Design Tokens Technical Reports 2025.10](https://www.designtokens.org/tr/2025.10/))၊ ([DTCG announcement](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/))၊ ([Style Dictionary](https://styledictionary.com/info/tokens/))။ Style Dictionary ဗားရှင်း ၄ သည် `$value`၊ `$type`၊ `$description` ပါ DTCG ပုံစံနှင့် မူလ `value`၊ `type`၊ `comment` ပုံစံ နှစ်မျိုးစလုံးကို ဖတ်နိုင်ပြီး၊ တစ်ခုတည်းသော instance ထဲတွင် ရောမသုံးရန် ၎င်း၏စာမျက်နှာက ပြောသည်။ ၂၀၂၅.၁၀ မော်ဂျူးအားလုံးကို အပြည့်အဝ ကာမိသည်ဟု ထိုစာမျက်နှာက မဆိုပါ။

React သည် ပထမပါတီ agent ကိရိယာ အများဆုံးသော framework ဖြစ်သည်။ Figma ၏ `get_design_context` မူလအထွက်မှာ React နှင့် Tailwind ဖြစ်သည် ([Figma MCP tools](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/))။ Storybook MCP သည် preview ဖြစ်ပြီး၊ Kyle Gach က ၂၀၂၆ မတ် ၂၃ (၂၀၂၆ စက်တင်ဘာ ၁၁ တွင် ပြင်ဆင်) တွင် Storybook 10.3 ၌ React အတွက် ရနိုင်ပြီဟု ရေးသည်။ အခြား framework များကို နှစ်အတွင်း နောက်မှ လာမည်ဟု ဆိုသည် ([Storybook MCP for React](https://storybook.js.org/blog/storybook-mcp-for-react/))။ shadcn/ui ၏ MCP သည် registry မှ component ကို ရှာပြီး တပ်ဆင်သည်။ တရားဝင်စာမျက်နှာက token ဖိုင် သို့မဟုတ် prop schema ကို မမှတ်တမ်းတင်ပါ ([shadcn MCP](https://ui.shadcn.com/docs/mcp))။ Vue နှင့် Angular သည် တစ်စိတ်တစ်ပိုင်းဖြစ်သည်။ SwiftUI သည် Code Connect ၏ label အဖြစ် ပေါ်ပြီး၊ မှတ်တမ်းတင်ထားသော MCP catalog အဖြစ် မပေါ်ပါ။

Supernova ၏ ၂၀၂၆ အောက်တိုဘာ ၅–၆ စစ်ဆေးမှုသည် “အဖွဲ့များ ယခု ဘာလုပ်ထားသလဲ” အတွက် အကြီးဆုံး နှိုင်းယှဉ်ဇယားဖြစ်သည်။ စစ်ဆေးချက်ငါးခု၊ တစ်ခုလျှင် နှစ်မှတ်။ **token ကို JSON သို့မဟုတ် JS အဖြစ် တပ်ဆင်နိုင်ခြင်း ၂၈/၃၁** က ပြည့်မှတ်၊ **typed component API ၂၆/၃၁** က နှစ်မှတ်၊ တရားဝင် MCP ကို စာသားက **၉ ခု** ဟု ဆိုသည်၊ agent က အပြည့်ဖတ်နိုင်သော စာရွက် **၃**၊ ထုတ်ကုန်အဖွဲ့အတွက် agent လမ်းညွှန် **၃**။ ၁၀ မှတ်ပြည့် မည်သူမျှ မရ။ `AGENTS.md` ရှိသော ၁၂ စနစ်လုံးသည် ဒီဇိုင်းစနစ် repo ထဲက ပံ့ပိုးသူအတွက် ရေးထားပြီး၊ ထုတ်ကုန် repo ထဲက အင်ဂျင်နီယာအတွက် မရေးပါ။ အမြင့်ဆုံးရမှတ်များဖြစ်သော Ant Design၊ Atlassian Design System၊ React Spectrum တို့သည် **၉/၁၀** ဖြစ်ပြီး consumer လမ်းညွှန် လစ်နေသည်။ IBM Carbon သည် ၈၊ GitHub Primer သည် ၇ ဖြစ်ပြီး တရားဝင် MCP နှင့် ပံ့ပိုးသူလမ်းညွှန်ရှိကာ `llms.txt` မရပါ။ အစိုးရစနစ်ငါးခု ပျမ်းမျှ **၃.၂**၊ ကျန် ၂၆ ခု ပျမ်းမျှ **၅.၆** ဖြစ်သည်။ ရမှတ်နိမ့်ခြင်းသည် လူသားအသုံးပြုသူအတွက် စနစ်မကောင်းဟု မဆိုကြောင်း Supernova က သတိပေးသည်။ ၎င်းတို့၏ ခန့်မှန်းချက်မှာ consumer လမ်းညွှန်နှင့် `llms.txt` နှစ်ဖိုင်ထည့်လျှင် median သည် ၅ မှ ၇ သို့၊ အပေါ်ပိုင်းအုပ်စုသည် ၉ စနစ်မှ ၂၆ သို့ ရွေ့မည်ဟု ဆိုသည် ([Supernova study](https://www.supernova.io/blog/ai-ready-design-systems-2026-study))။ GOV.UK၊ U.S. Web Design System၊ Fluent UI အတွက် ပိုင်ရှင်အဖွဲ့ပြင်ပက လုပ်ထားသော MCP များကို ဝယ်လိုအားအချက်ပြဖြစ်ပြီး၊ ပိုင်ရှင်စနစ်နှင့် ကွဲသွားနိုင်သော အန္တရာယ်အဖြစ် ထိုလေ့လာမှုက ရေးသည်။

အမည်ပါ အဖွဲ့အစည်းက ထုတ်ပြန်ထားသော စာချုပ်အသေးစိတ်သည် ဤရှာဖွေမှုတွင် နှစ်ခုထင်ရှားသည်။ Adobe ၏ Spectrum Design Data agent-surface spec သည် `1.0.0-draft` ဖြစ်ပြီး၊ ဖတ်ခြင်း၊ စစ်ခြင်း၊ token ရေးခြင်း ပို့ဆောင်လမ်းသုံးခု (CLI၊ MCP၊ Claude Code skill) ကို ဖော်ပြသည်။ `write_component` နှင့် `explain` / `get_guidance` သည် မပြီးသေးပါ။ `primer` ကို context **တိုကင် ၂,၀၀၀** ဝန်းကျင်ထားရန် အကြံပြုပြီး၊ အေးခဲနေသော `DESIGN.md` အကျဉ်းသည် dataset နှင့် ကွဲတတ်သောကြောင့် ရှင်သန်နေသော primer ဖြင့် အစားထိုးခဲ့သည်ဟု ရေးသည် ([Agent-readable surface](https://opensource.adobe.com/spectrum-design-data/spec/agent-surface/))။ စားသုံးသူ server `@adobe/design-data-mcp` သည် ဖတ်ခွင့်သီးသန့်ဖြစ်ပြီး၊ ထည့်သွင်းထားသော လမ်းညွှန်များသည် အများပြည်သူ Spectrum ဆိုက်ထက် နောက်ကျနိုင်သည် ([Using AI](https://opensource.adobe.com/spectrum-design-data/ai/))။ Gusto ၏ Jay Johnson က ၂၀၂၆ ဇူလိုင် ၂၇ နှင့် ဩဂုတ် ၃ တွင် Workbench ကို ရေးသည်။ component တစ်ခုစီတွင် Zod schema ရှိပြီး `.meta()` ထဲ၌ စစ်ပြီးသား ဥပမာ၊ အကြောင်းအရာလမ်းညွှန်၊ accessibility လမ်းညွှန်၊ `importStatement`၊ `figmaUrl` ပါသည်။ Button နှင့် Select သည် `.strict()` union ဖြစ်သောကြောင့် တရားမဝင် ပေါင်းစပ်မှုကို ကိုယ်စားမပြုနိုင်ပါ။ ညွှန်ကြားချက်မှာ **ဥပမာမှ ကူးပါ၊ မတီထွင်ပါနှင့်** ဖြစ်သည် ([Eval-Driven Design Systems](https://engineering.gusto.com/eval-driven-design-systems-8f781dc2dacb))။ schema package နှင့် MCP ရင်းမြစ်ကုဒ်ကို Gusto က မထုတ်ပြန်ပါ။ Shopify Polaris၊ GitHub Primer၊ Atlassian၊ IBM Carbon၊ Salesforce တို့၏ agent-facing ဗိသုကာကို ဤရှာဖွေမှုက အင်ဂျင်နီယာပို့စ်အဖြစ် မတွေ့ပါ။ မတွေ့ခြင်းသည် မရှိကြောင်း အထောက်အထားမဟုတ်ပါ။

ထုတ်ကုန် UX ဘက်တွင် ထုပ်ပိုးပြီးသား အများပြည်သူအပိုင်းအစသည် စည်းမျဉ်းစာမျက်နှာများနှင့် component kit အနည်းငယ်ဖြစ်သည်။ IBM Carbon for AI ကို ၂၀၂၆ ဩဂုတ် ၁၂ တွင် နောက်ဆုံးပြင်ထားပြီး၊ AI ကို သီးခြား theme အဖြစ် မခွဲဘဲ ပုံစံမုဒ်၊ AI label (ယခင် AI Slug)၊ explainability popover၊ “revert to AI”၊ လက်ရှိ component များ၏ AI မျိုးကွဲအဖြစ် ထုပ်သည်။ Chat သည် သီးခြား တည်ငြိမ်ပစ္စည်း `@carbon/ai-chat` ဖြစ်ပြီး ၁.၀.၀ ကို Anna Wen က ၂၀၂၅ အောက်တိုဘာ ၁၄ တွင် ကြေညာသည် ([Carbon for AI](https://www.carbondesignsystem.com/building-blocks/foundations/carbon-for-ai))။ Adobe `@react-spectrum/ai` က `PromptField`၊ `Chat`၊ `Thread`၊ `ResponseStatus`၊ `ExecutionTrace`၊ `PixelLoader` တို့ကို အမည်ပေးထားသည်။ `ExecutionTraceItem` ၏ အခြေအနေတန်ဖိုးများမှာ `failed`၊ `pending`၊ `success` ဖြစ်သည် ([AI Components](https://react-spectrum.adobe.com/ai-components))။ Amazon Cloudscape ၏ Generative AI chat ပုံစံကို ၂၀၂၄ နိုဝင်ဘာ ၂၀ တွင် ထုတ်ပြီး၊ chat bubble မှ support prompt group အထိ၊ ရေးသားစည်းမျဉ်း၊ loading၊ autoscroll တားမြစ်ချက်၊ `role="region"` တို့ကို တစ်မျက်နှာတည်းတွင် ထားသည် ([Generative AI chat](https://cloudscape.design/gen-ai/patterns/generative-ai-chat/))။ Salesforce က SLDS 2 ကို “agentic design system” ၏ အခြေခံဟု ခေါ်ပြီး styling hook၊ Agentic Experience Figma စာကြည့်တိုက် (“soon” ဟု ထိုပို့စ်က ရေးသည်)၊ unstyled primitive များကို ညွှန်သည်။ Agentforce အတွက် primitive များသည် အတွင်းပိုင်းဖြစ်ခဲ့ကြောင်း နောက်ပို့စ်က ဆိုသည်။ ဤပို့စ်များ၏ ရက်စွဲကို ရှာဖွေမှုက မရပါ။ SLDS 2 သည် Carbon for AI နှင့် တန်းတူ ထုတ်ပြန်ထားသော ပုံစံ catalog ဖြစ်သည်ဟု ဤမှတ်စုများက မသတ်မှတ်ပါ ([What is SLDS 2](https://www.salesforce.com/blog/what-is-slds-2/))။

လက်တွေ့ပျက်ကွက်မှုကို အမည်ပါစာများက ထပ်ပြောသည်မှာ တီထွင်ထားသော component နှင့် prop၊ တရားမဝင် enum၊ မှားသော import၊ hardcode အရောင်၊ ဟောင်းနေသော စာပိုဒ် သို့မဟုတ် Code Connect၊ ကြီးလွန်းသော Figma node နှင့် catalog ၏ context ကန့်သတ်ချက်၊ compile ဖြစ်နေဆဲဖြစ်သော accessibility နှင့် စာသားအမှားများ ဖြစ်သည်။ Gusto ၏ ဒုတိယပို့စ်တွင် မော်ဒယ်က `<Button variant="primary" intent="submit">` ဟု ရေးပြီး၊ `intent` သည် schema တွင် မရှိပါ။ `variant="large"` သည် prop ရှိသောကြောင့် prop-validity တစ်ခုတည်းက မမိနိုင်သော တန်ဖိုးအမှားဖြစ်သည်။ “payroll တင်သွင်းမှုကို အတည်ပြုပြီး ဆက်ရန် ခလုတ်ထည့်ပါ” ဟူသော prompt မှ “Confirm and continue” ထွက်ပြီး၊ အကြောင်းအရာစည်းမျဉ်းဖြစ်သော ကြိယာတစ်ခု၊ စကားလုံးသုံးလုံးအထိ ကို ကျော်သွားသည်။ ဤအထွက်သည် စက်မှုစစ်ဆေးချက်တွင် ပြည့်မှတ်ရနိုင်သည်။ Johnson က မှန်ကန်သော `importStatement` ကို ထုတ်ပြန်လိုက်ခြင်းက import အမှားတစ်မျိုးလုံးကို ပိတ်ခဲ့သည်ဟု ရေးသည် ([Part 2](https://engineering.gusto.com/eval-driven-design-systems-part-2-5b989d492281))။ `open-design-system-bench` က Aurora ဟု ခေါ်သော စနစ်တွင် `heading` prop ရှိလျက် `Heading` component ကို တီထွင်ခြင်း၊ `Text` ရှိလျက် `Typography` ကို သုံးခြင်း၊ Box နှင့် Card ပေါ်တွင် spacing prop တီထွင်ခြင်းကို hard fail အဖြစ် မှတ်သည် ([open-design-system-bench](https://github.com/christophhdesign/open-design-system-bench))။ Cristian Morales က ထို bench ကို သူ့စနစ်ပေါ် တိုင်းရာ၊ `AGENT.md`၊ `llms.txt`၊ skill ဖိုင်များက ဟောင်းသော ညွှန်ကြားချက်ပေးလျှင် အရည်အသွေးကျနိုင်ကြောင်း၊ ဖိုင်၏ ၉၀ ရာခိုင်နှုန်းခန့်ကို ဖျက်ပြီးနောက် ဆဲလ် ၉၀ ပြေးမှုတွင် ၇၂ ရပြီး၊ ထုတ်လုပ်ထားသော စာချုပ်သို့ ညွှန်ချက်နှင့် validation gate ကို ပြန်ထည့်သောအခါ ၉၀ သို့ ပြန်တက်ကာ တိုကင်ကုန်ကျမှု ၄၁ ရာခိုင်နှုန်းခန့် ကျသည်ဟု ရေးသည်။ စက်မှု ၁၀၀ နှင့် အကဲဖြတ် ၂၆ တွဲဖက်သော ကိစ္စကိုလည်း ဖော်ပြသည်။ ဤကိန်းများသည် အဖွဲ့စုံလေ့လာမှုမဟုတ်ပါ ([What does AI-Readiness mean in Design Systems?](https://www.giorris.dev/thoughts/what-does-ai-readiness-mean-in-design-systems))။

ညီလာခံအနှစ်ချုပ်က ဖော်ပြသော ပထမဆုံး အမှားမှာ ရှိပြီးသား Markdown ကို MCP တွင် ချိတ်ပြီး ယုတ္တိရှိသော အဖြေကို အောင်မြင်မှုဟု ယူခြင်းဖြစ်သည်။ Diana Wolosin ၏ Indeed စမ်းသပ်မှုကို Sil Bormüller က ၂၀၂၆ ဧပြီ ၁၀ တွင် ဤသို့ လွှဲပြောင်းသည်။ component ၇၇ ခု၊ MCP ဖွဲ့စည်းပုံ ၈ ခု၊ prompt ၁,၀၅၆ ခု။ Markdown သည် မေးခွန်းတစ်ခုလျှင် တိုကင် **၃၀,၀၀၀ ဝန်းကျင်**၊ coverage **၈၂ ရာခိုင်နှုန်း**၊ hallucination ပါသည်။ JSON သည် တိကျမှု ပိုမြင့်၊ တိုကင် **၈၀ ရာခိုင်နှုန်းခန့်** လျော့၊ နှစ်စဉ်ကုန်ကျမှု **၅ ဆခန့်** လျော့သည် ($၃၀၀ နှင့် $၁,၅၀၀)။ ဤကိန်းများကို Indeed ၏ ကိုယ်ပိုင်ပို့စ်နှင့် ပြန်မစစ်ရသေးပါ ([Your Design System Is Not Ready for AI Agents](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents))။

Chat ကို ထောင့်တွင် ကပ်လိုက်ခြင်းသည် ဒီဇိုင်းစနစ်တည်ဆောက်နည်းအဖြစ် ဤမှတ်စုများထဲတွင် ထပ်တလဲလဲ ကိုးကားချက်တစ်ခု မဖြစ်ပါ။ သီးခြားကျရှုံးမှုအဖြစ်မူ NN/g ၏ ၂၀၂၆ မတ် ၂၀ လေ့လာမှုက ရှိသည်။ ပါဝင်သူများသည် ဆိုက် chatbot ကို သတိမထားမိခြင်း၊ ဘာအတွက်လဲ မပြောနိုင်ခြင်း၊ ရှာဖွေမှုနှင့် filter ထက် တန်ဖိုးမမြင်ခြင်း ဖြစ်ခဲ့သည်။ Home Depot ၏ Magic Apron သည် သေး၊ အညွှန်းမပါ၊ ပုံဟု ထင်ရသည်။ Turo ၏ bot သည် “ask me anything” ဖြင့် ဖွင့်ပြီး အသုံးပြုသူကြိုးစားသော ယာဉ်ရှာအလုပ်ကို မလုပ်နိုင်ပါ။ ဆောင်းပါး၏ စည်းက အဖြေမရှိသေးသော ပြဿနာမှ စရန်ဖြစ်ပြီး၊ bot တစ်ခုထည့်ပြီး log ကြည့်ရန် မဟုတ်ပါ ([What Is Your Site's AI Chatbot for?](https://www.nngroup.com/articles/site-ai-chatbot/))။

## စစ်ဆေးချက်မရှိသော ဖတ်ခွင့်ကို ရင်းမြစ်များက မလုံလောက်ဟု သတ်မှတ်သည်

တည်ဆောက်သင့်သော စနစ်၏ ပူးတွဲအဓိပ္ပာယ်ကို Aestheria နှင့် Into Design Systems က ဤသို့ ထားသည်။ agent က ဖတ်နိုင်၊ အသုံးချနိုင်၊ ပြင်ပမှ စစ်နိုင်သော အခြေခံအဆောက်အအုံဖြစ်သည်။ agent က UI ထုတ်နိုင်ခြင်းတစ်ခုတည်းနှင့် မပြီးပါ ([Aestheria](https://aestheria.design/blog/what-is-an-agentic-design-system))။ Aestheria က agent က ထုတ်သည်၊ ကိုယ်တိုင် ပြန်သုံးသပ်သည်၊ တင်သည်ဆိုလျှင် ဘာကိုမျှ မစစ်ရသေးဘဲ ကိုယ့်ဘာသာ ကိုယ်သဘောတူထားခြင်းဖြစ်သည်ဟု ရေးသည်။ စစ်ရန် စံနှုန်းသည် token အစု၊ density နှင့် spacing စည်း၊ contrast အောက်ခြေ၊ component စာချုပ်၊ ပုံစံတစ်ခု ခွင့်ပြုထားသော state များ ဖြစ်သည်။ ဒီဇိုင်နာတစ်ဦး ကြည့်ခြင်းသာ ကျန်လျှင် ထိုအရာကို ပြန်လည်သုံးသပ်လုပ်ငန်းစဉ်ဟု ခေါ်ပြီး စနစ်ဟု မခေါ်ပါ။

အခြေခံအားနည်းသော အဖွဲ့အတွက် ညီလာခံအနှစ်ချုပ်၊ Matthew Huntsberry၊ Josef Richter တို့က အမည်၊ semantic token၊ စာချုပ်ကို agent ချိတ်ဆက်မှုမတိုင်မီ ရေးရန် ဆိုသည်။ Romina Kavcic ၏ အစီအစဉ်ကို “Plant seeds, not trees” ဟု အနှစ်ချုပ်က ဖော်ပြသည်။ အမည်ပေးစည်းမျဉ်း၊ token တည်ဆောက်ပုံ၊ component ဖော်ပြချက်မှ စပြီး၊ ပထမနေ့တွင် ကိုယ်ပိုင်အုပ်ချုပ်မှုအပြည့်ကို မလိုက်ပါ။ Brad Frost က ဤအကြံသည် maturity အဆင့်တိုင်းတွင် သက်ဆိုင်ပြီး၊ component တစ်ခုစီအတွက် JSON schema (identity၊ props၊ variants၊ sizes၊ states၊ usage) တစ်ခုသည် context လုံးဝမရှိခြင်းထက် ပိုကောင်းသည်ဟု ညီလာခံတွင် ပြောခဲ့ကြောင်း အနှစ်ချုပ်က ဆိုသည်။ Frost ၏ ၂၀၂၅ ဒီဇင်ဘာ ၁၆ ပို့စ်ကိုယ်တိုင်က ဤစာကြောင်းကို မပါပါ ([Into Design Systems](https://www.intodesignsystems.com/agentic-design-systems))၊ ([Sil Bormüller၊ ၂၀၂၆ ဧပြီ ၁၀](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents))။ Huntsberry ၏ AI Design Infrastructure Readiness Model တွင် တိုင် ၈ ခုကို ၁ မှ ၅ အထိ ပေးသည်။ Fragmented၊ Emerging၊ Documented၊ Governed၊ Automation-ready ဖြစ်သည်။ အစဉ်မှာ token taxonomy၊ Figma library၊ component API ချိန်ညှိမှု၊ typography နှင့် responsive၊ design နှင့် code ညီမျှမှု၊ စာရွက်စာတမ်း၊ accessibility နှင့် governance၊ နောက်ဆုံးမှ AI / MCP ဖြစ်သည်။ သူက ကျန်တိုင်များ လိုအပ်ပြီး တိုင် ၈ သည် ချိတ်ဆက်အလွှာသာဖြစ်သည်ဟု ရေးသည်။ token ကောင်းသောပုံမှာ primitive / semantic / component သုံးဆင့်၊ အဓိပ္ပာယ်ကို ဖော်သော အမည် (`color-text-secondary`၊ ပုံပန်းအမည် `gray-400` နေရာတွင်)၊ ရင်းမြစ်တစ်ခု၊ token တစ်ခုလျှင် ပိုင်ရှင်တစ်ဦး ဖြစ်သည်။ စာမျက်နှာတွင် ရက်စွဲမပါပါ ([The AI Design Infrastructure Readiness Model](https://www.mmhuntsberry.com/methodology))။ Richter က ၂၀၂၆ ဇူလိုင် “state of the art” ဟု သူမှတ်ထားသော အပိုင်းတွင် W3C DTCG JSON ကို canonical ထားရန်၊ Style Dictionary ဖြင့် compile လုပ်ရန်၊ ရည်ရွယ်ချက် metadata ကို MCP ဖြင့် ထုတ်ရန်၊ Code Connect ဖြင့် canvas သို့ ပြန်ချိတ်ရန် ရေးသည်။ primitive သာ ရေးပြီး အဓိပ္ပာယ်ကို `$description` စာကြောင်းထဲ ထားခြင်းကို လက်တွေ့တွင် အဖြစ်အများဆုံး အတိုကောက်ဟု ခေါ်သည်။ `DESIGN.md` ကို Google Labs ၏ ၂၀၂၆ ဧပြီ လက်ရာအဖြစ် သူက ရက်စွဲတပ်ပြီး၊ pre-1.0 ဖြစ်ကာ ထုတ်လုပ်မှုမှီခိုမှုအဖြစ် မလုံခြုံသေးဟု ဆိုသည်။ ထိုရက်စွဲကို W3C သို့မဟုတ် Google Labs မူရင်းစာမျက်နှာနှင့် ဤမှတ်စုများက ပြန်မစစ်ပါ။ DTCG ၂၀၂၅.၁၀ ၏ ၂၀၂၅ အောက်တိုဘာ ၂၈ ရက်စွဲကိုမူ Design Tokens Community Group ၏ ကိုယ်ပိုင်ကြေညာချက်က အတည်ပြုသည် ([Building an Agentic Design System](https://josefrichter.design/blog/agentic-design-system))။

token နှင့် typed API ရှိပြီးသား စနစ်အတွက် Supernova က အလုပ်အသေးဆုံးမှ စရန် အစီအစဉ်ပေးသည်။ နေ့လယ်တစ်ခုတွင် ထုတ်ကုန်အဖွဲ့အတွက် `AGENTS.md` ကို package ထဲ ထည့်သည်။ import လမ်းကြောင်း၊ token အမည်ပေးပုံ၊ hardcode တန်ဖိုးကို လက်မခံကြောင်း၊ agent လုပ်တတ်သော အမှားဆယ်ခု၊ ရပ်ဆိုင်းထားသည်များနှင့် အစားထိုးများ၊ MCP သို့မဟုတ် `llms.txt` နေရာတို့ ပါသည်။ getting-started ထဲတွင် ထုတ်ကုန် repo များကို ထိုဖိုင်ဖတ်ရန် တစ်ကြောင်း ထည့်သည်။ တစ်ရက်နှစ်ရက်တွင် `llms.txt`၊ ဖြစ်နိုင်လျှင် `llms-full.txt` သို့မဟုတ် စာမျက်နှာတိုင်း၏ markdown။ token JSON မရှိသေးလျှင် ရက်အနည်းငယ်။ component API ကို TypeScript၊ `custom-elements.json`၊ သို့မဟုတ် GOV.UK `macro-options.json` ကဲ့သို့ ဖိုင်များ။ အကြီးဆုံးအလုပ်မှာ ဖတ်ခွင့်သီးသန့် MCP ဖြစ်ပြီး၊ theme အလိုက် ဖြေရှင်းပြီးသော token၊ component API နှင့် အသုံးပြုစည်း၊ စာရွက်ရှာဖွေမှု၊ ရပ်ဆိုင်းမှုနှင့် အစားထိုးကို ထုတ်သည်။ Primer နှင့် PatternFly ၏ server များကို open-source ကိုးကားချက်အဖြစ် ညွှန်သည်။ ပထမအဆင့်နှစ်ခုကို အဖွဲ့အများစုအတွက် **တစ်ပတ်ခန့်** ဟု ဆိုသည် ([How to Make Your Design System Fully AI-Ready](https://www.supernova.io/blog/how-to-make-your-design-system-ai-ready))။ ဤအစီအစဉ်ကို အမည်မဲ့၊ စာပိုဒ်သီးသန့် စနစ်ပေါ် တင်လျှင် ညီလာခံ၏ “အခြေခံအရင်” အကြံနှင့် ပြောင်းပြန်ဖြစ်သွားသည်။ မှတ်စုများက နှစ်ခုစလုံး မှန်နိုင်သည်ဟု ကောက်ချက်ချသည်။ စတင်မှတ်တိုင် မတူသောကြောင့်ဖြစ်သည်။ ဘယ်ရင်းမြစ်ကမှ အခြားတစ်ခု မှားသည်ဟု မဆိုပါ။

ပုံစံမရွေးမီ ပြန်လည်ရယူမှုကို တိုင်းရန် Wolosin ၏ အစီရင်ခံထားသော စမ်းသပ်မှုကို ညီလာခံအနှစ်ချုပ်က တိုက်တွန်းသည်။ JSON သည် MCP အတွက် စာချုပ်၊ Markdown သည် မော်ဒယ်သို့ ညွှန်ကြားချက် ဖြစ်သည်။ အမြဲပါနေသော အခြေခံစည်း (spacing၊ color၊ typography)၊ လိုမှ မေးသော MCP၊ `AGENTS.md` ဟူသော ဖိုင်သုံးလွှာကို Kavcic နှင့် Frost ထံ အနှစ်ချုပ်က ရည်ညွှန်းသည်။ အကြောင်းရင်းမှာ MCP သည် prompt က မေးသောအရာသာ ပြန်ပေးသောကြောင့် “card တစ်ခု ဆောက်ပါ” ဟူသော prompt သည် spacing နှင့် type ကို မဆွဲတတ်ဘဲ မော်ဒယ်က ကွက်လပ်ဖြည့်သည်ဟု ဆိုသည်။ Frost ၏ ဒီဇင်ဘာ ၁၆ ပို့စ်တွင် ဤဖိုင်သုံးလွှာကို မရေးပါ။ MCP မချိတ်မီ token အမည်၊ component ဖော်ပြချက်၊ လက်ရှိ API စာရွက်တို့ အဓိပ္ပာယ်တူရန် စစ်ရန် Bormüller က Kavcic ကို ပြန်ပြောသည် ([Sil Bormüller](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents))။ Figma က မော်ဒယ်သည် token ကို အရင်ဖတ်တတ်ပြီး၊ အသုံးပြုစည်းမပါလျှင် မူလ variant ကို ရွေးတတ်သည်ဟု ရေးသည်။ prompt နှင့် rules ဖိုင်တွင် ရင်းနှီးမြှုပ်နှံမှု လွန်ကဲတတ်ပြီး၊ လစ်နေသော သွင်းအားသည် design context ဖြစ်သည်ဟု ညီအစ်မဆောင်းပါးက ဆိုသည် ([LLM Context Design](https://www.figma.com/resource-library/llm-context-design/))၊ ([Contextual AI coding](https://www.figma.com/resource-library/contextual-ai-coding/))။ Claude Code က `CLAUDE.md` ကို context ဟု သဘောထားပြီး အတင်းအကျပ်ဖွဲ့စည်းမှုမဟုတ်ကြောင်း၊ ပိတ်ချင်လျှင် PreToolUse hook လိုကြောင်း၊ ဖိုင်တစ်ခုလျှင် **လိုင်း ၂၀၀ အောက်** ထားရန်၊ ရှည်လျှင် လိုက်နာမှုကျကြောင်း ရေးသည်။ `AGENTS.md` ကို အလုပ်လုပ်နေသော လမ်းကြောင်းနှင့် အပေါ်တွင် `CLAUDE.md` သို့မဟုတ် `CLAUDE.local.md` မရှိမှ မူလအတိုင်း ဖတ်ပြီး၊ တိုက်ရိုက်ဖတ်ခြင်းသည် Claude Code **v2.1.277** နှင့် နောက်ပိုင်းတွင် ရှိသည် ([How Claude remembers your project](https://code.claude.com/docs/en/memory))။

Governance တွင် ရင်းမြစ်များ ဆုံသောအပိုင်းမှာ လူပိုင်ရှင်ရှိခြင်း၊ agent သည် ခေါ်သူလူ၏ ခွင့်ပြုချက်ဖြင့် လုပ်ခြင်း၊ ပြန်လည်သုံးသပ်နိုင်သော အထွက် (issue၊ draft၊ PR) ရေးခြင်း၊ breaking change ၏ ပိုင်ရှင် မဖြစ်ခြင်း ဖြစ်သည်။ ဘယ်အထိ agent သွားနိုင်သည်ကို မဆုံပါ။ Primer / Jan Six အား အနှစ်ချုပ်က issue သာ ဖွင့်စေပြီး merge မလုပ်စေဟု ဖော်ပြသည်။ Kavcic အား အနှစ်ချုပ်က လုပ်ဆောင်ချက်အလိုက် ယုံကြည်မှုပေးသည်။ ယုံကြည်မှုမြင့်၊ အန္တရာယ်နိမ့် (lint၊ စာလုံးပေါင်း၊ accessibility label) ကို auto-merge၊ အလယ် (token တန်ဖိုး၊ component ဖော်ပြချက်) ကို draft PR၊ API အသစ်၊ breaking change၊ governance ကို suggest-only ထားသည်။ အချို့ဆုံးဖြတ်ချက်သည် တတိယအဆင့်ကို မကျော်ဟု ဆိုသည် ([Sil Bormüller](https://www.intodesignsystems.com/blog/design-system-not-ready-for-ai-agents))။ zeroheight ၏ Seb Sidbury က ၂၀၂၆ အောက်တိုဘာ ၁၅ တွင် MCP-Write သည် app ထဲက ခွင့်ပြုချက်ကို ထင်ဟပ်ကြောင်း၊ စာမျက်နှာအသစ်နှင့် ပြင်ဆင်ချက်သည် draft အရင်ဖြစ်ကြောင်း၊ အစုလိုက် အလိုအလျောက်လုပ်ငန်းအတွက် merge ကို MCP မှ လုပ်ခွင့်ပေးထားကြောင်း၊ အစုမပေါင်းမီ အစိတ်အပိုင်းတစ်ခုကို စမ်းရန် ရေးသည်။ ထိုရက်စွဲတွင် token စီမံမှု၊ release၊ setting၊ styleguide အသစ်၊ Figma သို့မဟုတ် Storybook ဖိုင်ထည့်ခြင်းသည် နယ်ပယ်ပြင်ပဖြစ်သည် ([MCP-Write](https://zeroheight.com/blog/mcp-write-what-changes-when-ai-can-write-to-your-design-system/))။ Supernova က ဒီဇိုင်းစနစ် MCP ကို ဖတ်ခွင့်သီးသန့် စတင်ရန် ဆိုသည်။ Nathan Curtis က ၂၀၂၆ အောက်တိုဘာ ၂၈ ထုတ် Wireframe အစီအစဉ်တွင် spec ကို agent ဖြင့် Figma မှ ပြန်မထုတ်ရန်၊ script ဖြင့် စာချုပ်ကို အရင် ငြမ်းထောင်ပြီးမှ agent က ပြင်ဆင်ရန်၊ screenshot ကို မော်ဒယ်ထဲ ထည့်သော ၂၀၂၅ အစောပိုင်းအလေ့အကျင့်ကို ပယ်ရန် ပြောသည် ([Specs Made Spectacular](https://exa.ai/library/podcast/t3g656dlr7n/episode/g11qn6nwdv7))။ HashiCorp Helios ၏ တရားဝင် MCP သည် ဖတ်ခွင့်သီးသန့်ဖြစ်ပြီး ဖိုင်မပြင်၊ dependency မတပ်၊ ပရောဂျက်ကို မပြင်ဟု ရေးသည် ([Helios MCP](https://helios.hashicorp.design/tooling/mcp-server))။

Evaluation အတွက် မျှဝေထားသော လုပ်ငန်းစံမရှိပါ။ “Golden tasks” ဆိုသော အမည်ကို ဤရင်းမြစ်များထဲတွင် မတွေ့ပါ။ အနီးစပ်ဆုံး အများပြည်သူပစ္စည်းမှာ Indeed ၏ ပြန်လည်ရယူမှုစမ်းသပ်မှု (ညီလာခံမှတစ်ဆင့်) နှင့် Gusto ၏ Braintrust scorer များဖြစ်သည်။ Gusto က prompt ၁၆၇ ခု၊ component ၂၅ ခု၊ အင်ဂျင်နီယာတောင်းဆိုမှု ဒုတိယအစု၊ scorer သုံးခု (`prop-validity`၊ `enum-validity`၊ `import-match`) နှင့် လူသားအကဲဖြတ်နှစ်ခု (intent၊ idiom) ကို ဖော်ပြသည်။ စုစုပေါင်းဂဏန်းကို မထုတ်ပါ။ အနည်းဆုံးအကြံမှာ component ငါးခု၊ prop အမျိုးအစားပါ schema၊ စစ်ပြီးသား ဥပမာသုံးခု၊ တိကျသော import၊ ရိုးရိုးအင်္ဂလိပ် prompt ဆယ်ခုစီ၊ အနည်းဆုံး `prop-validity`၊ schema ပြောင်းတိုင်း ပြန်ပြေးရန် ဖြစ်သည် ([Part 2](https://engineering.gusto.com/eval-driven-design-systems-part-2-5b989d492281))။ `open-design-system-bench` က အလုပ်တစ်ခုကို မော်ဒယ်တစ်ခုလျှင် မူလ ၃ ကြိမ် ပြေးပြီး **အဆိုးဆုံးအကြိမ်** ကို ယူသည်။ အလေးချိန်မှာ imports ၀.၁၀၊ apiFidelity ၀.၂၅၊ tokenDiscipline ၀.၁၅၊ a11yStatic ၀.၁၀၊ compile ၀.၁၀၊ judgment ၀.၃၀ ဖြစ်သည်။ တီထွင် component သည် hard fail ဖြစ်ပြီး၊ Gusto ၏ `prop-validity` သည် အပိုင်းအစမှတ်ဖြစ်သည်။ “မက်ထရစ်” ကို ကူးမည့်အဖွဲ့သည် ဤစာချုပ်နှစ်ခုအနက် ဘယ်တစ်ခုကို ဆိုလိုသလဲ ရွေးရမည် ([open-design-system-bench](https://github.com/christophhdesign/open-design-system-bench))။ Murphy Trueman က စက်မှုစစ်ဆေးချက်နှင့် အကဲဖြတ်ကို ခွဲပြီး၊ မော်ဒယ်အပ်ဒိတ်နှင့် `AGENTS.md` ပြင်ဆင်မှုသည် ကုဒ်ပြန်လည်သုံးသပ်မှုတွင် မပေါ်သောကြောင့် CI တွင် ပြေးရန် ရေးသည်။ suite တစ်ခုကို မထုတ်ပါ ([Design systems need evals](https://blog.murphytrueman.com/design-systems-need-evals/))။ Storybook ၏ `test-run` သည် agent ရေးသော story ပေါ်က interaction နှင့် accessibility ကို ပြန်ပေးပြီး၊ ဘယ် component ကို သုံးသင့်သလဲကို ဤအထောက်အထားတွင် မသိပါ ([Storybook MCP](https://storybook.js.org/docs/ai/mcp/overview))။ Spotify Encore ၏ အလွှာခွဲမှု၊ မော်ဒယ်စုံ eval၊ စတိုင်အသုံး ၂၂၀,၀၀၀ ကျော်၊ developer ကျေနပ်မှု ၉၃ ရာခိုင်နှုန်းတို့သည် Into Design Systems မှတစ်ဆင့်သာ သိရပြီး၊ eval ကြောင့် ဖြစ်ကြောင်း ဤမှတ်စုများက မသက်သေပြပါ။

အလိုအလျောက်မလုပ်သေးရမည့် စာရင်းကို ဒီဇိုင်းစနစ်ဦးဆောင်သူများက တရားစီရင်မှုဘက်တွင် ထားသည်။ API အသစ်၊ breaking change၊ governance၊ spec ကိုယ်တိုင်ကို ထုတ်ခြင်းတို့ ဖြစ်သည်။ Richter က `DESIGN.md` ကို ထုတ်လုပ်မှုမှီခိုမှု မယူရန်၊ DTCG ဘေးတွင် ရင်းမြစ်ဒုတိယခု မခွဲရန် ရေးသည်။ Sidbury က ပထမနေ့တွင် စာရွက်လုပ်ငန်းစဉ်တစ်ခုလုံးကို အလိုအလျောက်မလုပ်ရန်၊ အစိတ်မစမ်းဘဲ အစုလိုက် merge မလုပ်ရန် ရေးသည်။ Figma ၏ ဒီဇိုင်နာများအတွက် MCP ဆောင်းပါးက server သည် ဆုံးဖြတ်ချက်ကို အစားမထိုးနိုင်၊ ဆုံးဖြတ်ချက် ဘာကြောင့်လဲကို မရှင်းနိုင်ဟု ဆိုသည် ([MCP for Designers](https://www.figma.com/resource-library/mcp-for-designers/))။ Help Center က server တစ်ခုတည်းက ကုဒ်ကို မပြီးစေဟု ဆိုသည် ([Figma MCP server FAQs](https://help.figma.com/hc/en-us/articles/39252411778583-Figma-MCP-server-FAQs))။ Frost က ၂၀၂၅ ဒီဇင်ဘာ ၁၆ တွင် ကန့်သတ်မထားသော ထုတ်လုပ်မှုကို vibe coding ဟု ခေါ်ပြီး၊ ဒီဇိုင်းစနစ်ပစ္စည်းများအတွင်း ထုတ်လုပ်ရန် ထောက်ခံသည်။ လက်ဖြင့်ကျန်ရမည့် အလုပ်စာရင်းကို မထုတ်ပါ။ ၂၀၂၆ နိုဝင်ဘာ ၁၈ တွင် TJ Pitre ၏ စကားကို ကိုးကားသည်။ စစ်အင်ဂျင်မီးလင်းနေသော ကားနောက်တွင် ဒုံးပျံမတပ်ပါနှင့် ([Skills to pay the bills](https://bradfrost.com/blog/post/skills-to-pay-the-bills/))။ အမြင်ဒီဇိုင်းရှာဖွေမှု၊ brand၊ အသံနေအသံထား၊ သုတေသနပေါင်းစပ်မှုတို့အတွက် “မလုပ်ရသေး” စာရင်းကို ဤရှာဖွေမှုထဲက ဒီဇိုင်းစနစ်ဦးဆောင်သူတစ်ဦးက မထုတ်ထားပါ။

## အသေးစားအဖွဲ့သည် တံခါးနှစ်ချပ်ကို အစီအစဉ်အဖြစ် လိုက်သည်

၁–၁၀ ဦးအဖွဲ့အတွက် ရေးထားသော RFC၊ W3C မှတ်စု၊ အများပြည်သူ GitHub RFC ကို ဤရှာဖွေမှုက မတွေ့ပါ။ ညီလာခံလက်မှတ် သို့မဟုတ် အခပေးသင်တန်းမလိုဘဲ လိုက်နိုင်သော အများပြည်သူပစ္စည်းများမှာ Supernova ၏ အဆင့်ငါးဆင့်၊ Huntsberry ၏ တိုင်ရှစ်တိုင်၊ Richter ၏ DTCG-အရင် ပိုက်လိုင်း၊ Aestheria ၏ ကြိုတင်သတ်မှတ်ချက်သုံးခု၊ Sidbury ၏ လုပ်ငန်းစဉ်တစ်ခုတည်း စတင်နည်းတို့ ဖြစ်သည်။ ဘယ်စာရေးသူကမျှ ထိုပစ္စည်းကို “၁–၁၀ ဦးအတွက်” ဟု တံဆိပ်မကပ်ပါ။ Designesy ၏ ဆယ်ချက်စာချုပ်တွင် `robots.txt`၊ Open Graph၊ Twitter meta ကဲ့သို့ ဝဘ်ဆိုက်သန့်ရှင်းရေးပါပြီး၊ ညီလာခံဟောပြောသူများက ဒီဇိုင်းစနစ်အလေ့အကျင့်အဖြစ် မတင်ပြထားပါ။ zeroheight ၏ AI Readiness အဆင့်အမည်များသည် စျေးကွက်စာမျက်နှာတွင် မပါသောကြောင့် ဤနေရာတွင် မကိုးကားပါ။ အောက်ပါအစီအစဉ်သည် ထိုရင်းမြစ်များ၏ အစီအစဉ်ကို အခြေအနေအလိုက် ဆက်ထားခြင်းဖြစ်ပြီး၊ ရက်သတ္တပတ်အတု သို့မဟုတ် ရမှတ်ပစ်မှတ်အသစ် မထည့်ပါ။

### အခြေအနေကို မှတ်နှစ်ခုဖြင့် အရင် တိုင်းသည်

ပထမတံခါးသည် Huntsberry ၏ ပထမခုနစ်တိုင်နှင့် ညီလာခံ၏ “မျိုးစေ့” ဖြစ်သည်။ token အမည်က အရောင်ကုဒ်လော၊ Figma နှင့် ကုဒ်က နာမည်မတူလော၊ component တွင် props၊ variants၊ states ပါသော စာချုပ်ရှိလော၊ စာရွက်နှင့် token နှင့် API က တစ်ခုကို တစ်ခု ငြင်းလော။ ဒုတိယတံခါးသည် Supernova ၏ ငါးချက်ဖြစ်သည်။ တပ်ဆင်နိုင်သော token၊ typed API၊ agent ဖတ်နိုင်သော စာရွက်၊ ထုတ်ကုန်အဖွဲ့အတွက် လမ်းညွှန်၊ တရားဝင် MCP။ အများပြည်သူစနစ် ၃၁ ခုတွင် ပထမနှစ်ချက် ပြည့်ခါနီးပြီး နောက်ဆုံးသုံးချက် လစ်နေသည်။ အသေးစားအဖွဲ့သည် ကိုယ့် repo ကို ထိုငါးချက်ဖြင့် ရေတွက်ပြီး ဘယ်တံခါးတွင် ရပ်နေသလဲ ရေးမှတ်မှ နောက်အဆင့်ကို ရွေးနိုင်သည်။ Supernova က အနိမ့်ရမှတ်သည် လူသားအတွက် စနစ်အရည်အသွေးကို မပြောကြောင်း သတိပေးထားပြီးဖြစ်သည်။ Aestheria က agent မစတင်မီ လုပ်ရန် သုံးခုကို အရွယ်အစားမခွဲဘဲ ရေးသည်။ ကျရှုံးနိုင်သော စည်းမျဉ်းရေးပါ၊ ထုတ်လုပ်ထားသော UI ကို စစ်မည့် ပြင်ပစံကို အမည်ပေးပါ၊ ထုတ်လုပ်မှု UI ကို agent မရေးမီ ကြည့်ရှု၊ ကျော်လွန်၊ ပြန်လှန်လမ်းကို ဆုံးဖြတ်ပါ ([Aestheria](https://aestheria.design/blog/what-is-an-agentic-design-system))။

### အခြေခံမပြည့်လျှင် အမည်၊ semantic token၊ JSON စာချုပ်ကို အရင် ရေးသည်

ဤအခြေအနေတွင် Supernova ၏ “နေ့လယ်တစ်ခုနှင့် `AGENTS.md`” ကို အရင်မလုပ်ပါ။ ညီလာခံအနှစ်ချုပ်က တနင်္လာနေ့တွင် စနိုင်သော အလုပ်အဖြစ် အမည်ပေးခြင်း၊ token တည်ဆောက်ပုံ၊ component ဖော်ပြချက်ကို ထားသည်။ ဆက်လက်ရမည့် အစီအစဉ်ကို ဟောပြောသူအလိုက် ဤသို့ ပြန်ပြောသည်။ အလိုအလျောက်မလုပ်မီ အခြေခံ (Kavcic)၊ စာပိုဒ်အစား component တစ်ခုလျှင် JSON schema (Wolosin)၊ Figma ဖော်ပြချက်တွင် spec သာမက ရည်ရွယ်ချက်နှင့် ဖွဲ့စည်းပုံ (Kavcic)၊ လုပ်ဆောင်ချက်အလိုက် ယုံကြည်မှု (Kavcic)၊ `danger.background` ကဲ့သို့ semantic အမည်နှင့် parse လုပ်နိုင်သော front-matter (Jan Six)၊ MCP ပုံစံမသတ်မှတ်မီ JSON၊ Markdown၊ hybrid ကို တကယ့်မေးခွန်းများဖြင့် တိုင်းခြင်း (Wolosin)၊ အပတ်စဉ် အစည်းအဝေးအစား developer နှင့် တွဲရေးခြင်း (Kavcic)။ MCP မချိတ်မီ token အမည်၊ component ဖော်ပြချက်၊ လက်ရှိ API စာရွက်တို့ တူညီကြောင်း စစ်သည်။ Richter နှင့် Huntsberry နှစ်ဦးစလုံးက primitive ကို component က တိုက်ရိုက်မသုံးဘဲ semantic အလွှာကို ဖြတ်စေသည်။ ဥပမာ repo `gnegreiros-ux/agentic-design-system` က ထိုစည်းကို ဖိုင်ခွဲပုံနှင့် token စစ် script အဖြစ် ပြသည်။ ကုမ္ပဏီဖြစ်ရပ်လေ့လာမှုမဟုတ်ပါ ([agentic-design-system](https://github.com/gnegreiros-ux/agentic-design-system))။ Huntsberry က token တစ်ခုလျှင် ပိုင်ရှင်၊ Figma ထုတ်ဝေမှုကို သေးငယ်သော ပြန်လည်သုံးသပ်အုပ်စု၊ variant ဝင်ရိုးနှင့် engineering prop တစ်ခုချင်း ကိုက်ညီမှု၊ Figma နှင့် ကုဒ်တွင် တစ်ပြိုင်နက် ရပ်ဆိုင်းမှု၊ ဆုံးဖြတ်ချက်မှတ်တမ်း (ဘာကြောင့်)၊ CI ထဲက accessibility ကို “နောက်မှ ထုတ်ကုန်အဖွဲ့က ထည့်မည်” အဖြစ် မချန်ရန် ရေးသည်။ agent အကူအညီဖြင့် လာသော ပြင်ဆင်ချက်သည် ပြန်လည်သုံးသပ်လမ်း မရှိသောကြောင့် ရှောင်ကွင်းသွားတတ်သည်ဟု သူက ပျက်ကွက်ပုံကို ဖော်သည်။

### token နှင့် API ပြည့်လျှင် လမ်းညွှန်နှစ်ဖိုင်ကို တစ်ပတ်အတွင်း ထုတ်သည်

ဤအခြေအနေသည် Supernova က အများပြည်သူစနစ် ၃၁ ခုတွင် တွေ့သော အခြေအနေဖြစ်သည်။ ပထမဖိုင်သည် ထုတ်ကုန်အဖွဲ့ဖတ်သော `AGENTS.md` ဖြစ်သည်။ package ထဲ ထည့်ပြီး getting-started မှ ညွှန်သည်။ Porsche နှင့် DB UX ကဲ့သို့ ဖိုင်ကို package ထဲ ထားပြီး README က မဖော်ပြလျှင် ထုတ်ကုန် repo ထဲက agent က မမြင်ကြောင်း လေ့လာမှုက ဥပမာပေးသည်။ ဖိုင်ထဲတွင် ရပ်ဆိုင်းထားသော အရာနှင့် အစားထိုး၊ မသွင်းရသော package၊ hardcode တန်ဖိုးကို လက်မခံကြောင်း ပါရမည်ဟု Supernova က ရေးသည်။ Claude Code သုံးလျှင် ဤဖိုင်သည် `CLAUDE.md` ရှိနေသောအခါ မူလအတိုင်း မဝင်သောကြောင့်၊ ညွှန်ကြားချက်တိုကို Claude က ဖတ်သော ဖိုင်ထဲသို့ ထားရန် ၎င်း၏ memory စာရွက်က လိုအပ်သည်။ ရှည်သော ညွှန်ကြားချက်သည် လိုက်နာမှုကို လျှော့ပြီး၊ ဆန့်ကျင်သော ညွှန်ကြားချက်ကို Claude က တစ်ခုကို အလိုအလျောက် ရွေးနိုင်သည်။ Morales ၏ တစ်ခုတည်းသောစနစ်တိုင်းတာမှုတွင် ဟောင်းနေသော စာရင်းကို ဖိုင်ထဲ hardcode ထားခြင်းက ရမှတ်ကို ကျစေသည်။ ဒုတိယဖိုင်သည် `llms.txt` ဖြစ်သည်။ Supernova က ဤနှစ်ဖိုင်ကို တစ်ပတ်ခန့်ဟု ခန့်မှန်းသည်။ `llms.txt` ကို ဒီဇိုင်းစနစ် RFC အဖြစ် ဘယ်ရင်းမြစ်ကမျှ မတင်ပြပါ။

Catalog ကို မေးရမည့် မျက်နှာပြင်အဖြစ် ပိတ်သည်။ Figma၊ Storybook၊ v0၊ Gusto တို့၏ လုပ်ငန်းစည်းမှာ အမည်၊ prop၊ variant၊ import၊ token လမ်းကြောင်းသည် tool သို့မဟုတ် schema အဖြေမှ လာသည်ဟူ၍ ဖြစ်သည်။ Storybook ၏ `AGENTS.md` စတင်စာသားက UI မလုပ်မီ MCP ကို ခေါ်ရန်၊ `shadow` ကဲ့သို့ ရင်းနှီးသော prop ကိုပင် စာရွက်တွင် ရှိမှ သုံးရန်၊ `docs-list` ပြီးမှ `docs-show` လုပ်ရန်၊ မှတ်တမ်းမရှိသော prop ကို အမည်ဓလေ့ဖြင့် မယူဆရန် ရေးသည်။ `docs-show` သည် ပထမ story သုံးခုကိုသာ inline လုပ်သောကြောင့် နောက် story ထဲက variant သည် `docs-show-story` မခေါ်လျှင် မမြင် ([Storybook MCP](https://storybook.js.org/docs/ai/mcp/overview))။ Figma ၏ စည်းအစီအစဉ်မှာ `get_design_context`၊ ကြီးလွန်းလျှင် `get_metadata` ပြီးမှ လိုသော node သာ ပြန်ယူ၊ ထို့နောက် screenshot၊ ထို့နောက်မှ အကောင်အထည်ဖော်ခြင်း ဖြစ်သည်။ React နှင့် Tailwind အထွက်ကို ဒီဇိုင်း၏ ကိုယ်စားပြုမှုအဖြစ် သဘောထားပြီး၊ ပရောဂျက်၏ token နှင့် component ဖြင့် အစားထိုးရန် ရေးသည်။ ပုံနှင့် token ငြင်းလျှင် token ကို ဦးစားပေးပြီး spacing ကို အနည်းငယ်ညှိရန် ဆိုသည် ([Add custom rules](https://developers.figma.com/docs/figma-mcp-server/add-custom-rules/))။ Code Connect မရှိလျှင် agent သည် ရှိပြီးသား ထုတ်လုပ်မှု component ကို မညွှန်ဘဲ ပုံတူကို ထုတ်တတ်သည်ဟု Figma က ရေးသည်။ server သည် ဒီဇိုင်းမှ ကုဒ်ပြီးမြောက်ရေး တစ်ချက်တည်းလမ်းမဟုတ်ကြောင်း Help Center က ဆိုသည်။ ဝေးလံသော server လိပ်စာမှာ `https://mcp.figma.com/mcp` ဖြစ်သည်။ MCP ကို ဖတ်ခွင့်သီးသန့်ထားပြီး၊ ရပ်ဆိုင်းမှုနှင့် အစားထိုးကို အနည်းဆုံး မျက်နှာပြင်ထဲ ထည့်ရန် Supernova က ဆိုသည်။ Adobe က အေးခဲစာပိုဒ်အစား တိုကင် ၂,၀၀၀ ဝန်းကျင် primer နှင့် `validate_usage` ကို ထုတ်ထားသည်။ spec သည် draft ဖြစ်ပြီး component ရေးခြင်း မပြီးသေးသောကြောင့်၊ အသေးစားအဖွဲ့က ကူးနိုင်သော အပိုင်းသည် ရှင်သန်နေသော အကျဉ်းချုပ်နှင့် ပြင်ပ validator ဖြစ်သည်။ Gusto ပုံစံဖြင့် သွားလျှင် တရားမဝင် ပေါင်းစပ်မှုကို schema ထဲ မကိုယ်စားပြုနိုင်အောင် ပိတ်ပြီး၊ ဥပမာမှ ကူးရန် ညွှန်ကြားချက်တိုတစ်ခု ထားသည်။

ပုံစံကို မသတ်မှတ်မီ ပြန်လည်ရယူမှုကို တိုင်းသည်။ ညီလာခံအနှစ်ချုပ်က Markdown၊ JSON၊ hybrid ကို တကယ့်မေးခွန်းဖြင့် ယှဉ်ပြီးမှ MCP ပုံစံရွေးရန် ဆိုသည်။ ထိုကိန်းများသည် ဒုတိယလက် အစီရင်ခံချက်ဖြစ်၍၊ အသေးစားအဖွဲ့သည် $၃၀၀ နှင့် $၁,၅၀၀ ကို ပစ်မှတ်အဖြစ် မယူဘဲ၊ ကိုယ့် component အစုံပေါ်တွင် တိုကင်၊ coverage၊ တီထွင်ထားသော prop ကို ယှဉ်ရန်သာ ယူသည်။ UI ထုတ်မှုကို စစ်မည်ဆိုလျှင် Gusto ၏ အနည်းဆုံးအတိုင်းအတာ (component ငါးခု၊ ဥပမာသုံးခု၊ တိကျသော import၊ prompt ဆယ်ခုစီ၊ `prop-validity`၊ schema ပြောင်းတိုင်း ပြန်ပြေး) သည် ပိုင်ရှင်အဖွဲ့က ထုတ်ပြန်ထားသော အနိမ့်ဆုံးဘားဖြစ်သည်။ bench ၏ hard fail နှင့် Gusto ၏ အပိုင်းအစမှတ်သည် စာချုပ်မတူပါ။ Storybook `test-run` သည် story ထဲက contrast နှင့် interaction ကို ဖမ်းနိုင်ပြီး၊ မှားသော component ရွေးမှုကို မဖမ်းပါ။ Figma၊ Storybook၊ shadcn၊ v0၊ Claude တရားဝင်စာရွက်များတွင် agent က PR မဖွင့်မီ api-fidelity ရမှတ်အနိမ့်ဆုံးကို မသတ်မှတ်ထားပါ။

### ရေးခွင့်ကို လူတစ်ဦး၏ ခွင့်ပြုချက်နှင့် ပြန်လည်သုံးသပ်နိုင်သော အထွက်တွင် ထားသည်

ဖတ်လမ်း အလုပ်လုပ်ပြီးမှ ရေးလမ်းကို ဖွင့်သည်။ Sidbury ၏ အသေးစားအစီအစဉ်မှာ လုပ်ငန်းစဉ်တစ်ခု ရွေး၊ login ဖြင့် MCP ချိတ်၊ ရင်းမြစ်စနစ်များ ချိတ်၊ template ပေး၊ skill သို့မဟုတ် prompt သုံး၊ draft ကို ပြန်ကြည့်၊ ထို့နောက် ချဲ့ရန် ဖြစ်သည်။ အစိတ်တစ်ခုကို မစမ်းဘဲ အစုလိုက် merge မလုပ်ပါ။ ၂၀၂၆ အောက်တိုဘာ ၁၅ အထိ zeroheight ၏ ရေး API သည် token၊ release၊ setting ကို မလုပ်ပါ။ Kavcic ပုံစံကို လိုက်လျှင် auto-merge သည် lint၊ စာလုံးပေါင်း၊ accessibility label တွင် ရပ်ပြီး၊ API အသစ်၊ breaking change၊ governance သည် suggest-only တွင် ရပ်သည်။ Primer ပုံစံကို လိုက်လျှင် agent ၏ အထွက်သည် issue ဖြစ်ပြီး merge မဟုတ်ပါ။ ဤနှစ်ပုံစံကို မှတ်စုများက တစ်ခုတည်းသို့ မပေါင်းပါ။ Curtis ပုံစံကို လိုက်လျှင် spec ထုတ်ယူမှုနှင့် breaking / minor / patch ခွဲခြားမှုသည် script ဖြစ်ပြီး၊ agent သည် ငြမ်းပြီးသော စာချုပ်ကို ပြင်ဆင်သည်။ screenshot တစ်ခုချင်းနှင့် component တစ်ခုချင်း MCP ထိုးခြင်းကို သူက ပယ်သည်။ စာကြည့်တိုက်တစ်ခုလုံးကို script ဖြင့် spec ဖြစ်အောင် လုပ်ခြင်းကို သူက လိုချင်သည်။ Richter ပုံစံကို လိုက်လျှင် agent သည် စာချုပ်ကွက်လပ်ကို အဆိုပြုပြီး၊ အထွက်အောင်ရန် စည်းကို ပြန်မရေးပါ။ `DESIGN.md` ကို ထုတ်လုပ်မှုမှီခိုမှုအဖြစ် မယူပါ။

ထပ်တလဲလဲ အဖွဲ့အစည်းအမှားများက ဤတံခါးများကို ပြောင်းပြန်လှန်ထားသည်။ Markdown ကို စာချုပ်မရှိဘဲ MCP တွင် ချိတ်ခြင်း။ စာရွက်၊ token၊ component မတူဘဲ agent က ပထမရင်းမြစ်ကို ယူခြင်း သို့မဟုတ် ပျမ်းမျှခြင်း။ semantic အလွှာမရှိဘဲ `gray-400` သို့မဟုတ် `red-500` ကို တိုက်ရိုက်ကိုးကားခြင်း။ AI ပြင်ဆင်ချက်အတွက် ပံ့ပိုးလမ်းမရှိခြင်း။ `AGENTS.md` ကို ပံ့ပိုးသူအတွက်သာ ရေးခြင်း။ MCP တစ်ခုတည်းဖြင့် အခြေခံစည်းကို အမြဲပါအောင် မထားခြင်း (ဤအချက်သည် ညီလာခံအနှစ်ချုပ်ထဲက Frost ရည်ညွှန်းချက်ဖြစ်ပြီး ဒီဇင်ဘာ ၁၆ ပို့စ်၏ စာသားမဟုတ်ပါ)။ ယုံကြည်မှုအဆင့်မရှိဘဲ merge လုပ်ပိုင်ခွင့်ပေးခြင်း။ ထုတ်လုပ်မှုကို စနစ်ဟု ယူဆခြင်း။ Figma က MCP server သည် coder ကိုယ်တိုင်မဟုတ်ကြောင်း၊ မပေးထားသော စည်းမျဉ်းကို agent က မသိကြောင်း Help Center က ရေးသည်။ Spotify Encore အား အနှစ်ချုပ်က ဖော်ပြသော ကျရှုံးမှုမှာ props၊ style၊ behavior၊ accessibility၊ usage ကို ဖိုင်တစ်ခုတည်းတွင် ထားသောကြောင့် developer များက Cursor ကို အရင်မေးပြီး Encore မဟုတ်သော UI ကို တင်ခဲ့ခြင်းဖြစ်သည်။ Supernova ၏ ရက်စွဲမပါ “preparing” ဆောင်းပါးကလည်း စနစ်တစ်ခုလုံးကို ပြတင်းပေါက်ထဲ ထည့်လျှင် သက်ဆိုင်ရာအပိုင်းသာ ပေးခြင်းထက် ပိုဆိုးသည်ဟု ရေးသည် ([preparing article](https://www.supernova.io/blog/ai-ready-design-systems-preparing-your-design-system-for-machine-powered-product-development))။ “Figma ဖိုင်တစ်ခုလုံးကို prompt ထဲ မထည့်ပါနှင့်” နှင့် “chatbot UI ကို ဒီဇိုင်းစနစ်ဟု မသတ်မှတ်ပါနှင့်” ဆိုသော ဝါကျများကို ဤရင်းမြစ်များက မရေးထားပါ။

### agent မျက်နှာပြင်ပုံစံကို ဤအစီအစဉ်ထဲသို့ မထည့်ပါ

ထုတ်ကုန်ထဲက agent မျက်နှာပြင်သည် Meaning B ဖြစ်ပြီး၊ အပေါ်က တံခါးများသည် Meaning A နှင့် ကန့်သတ်ထားသော Meaning C ဖြစ်သည်။ နှစ်ခုကို တစ်ခုတည်းသော backlog ဖြစ်အောင် ရောလျှင်၊ component ပိုက်လိုင်းနှင့် chat၊ handoff၊ confidence UI ကို ရင်းမြစ်များ မရောထားသော နည်းဖြင့် ရောမိသည်။ ၂၀၂၆ နှောင်းပိုင်းတွင် ရင်းမြစ်တစ်ခုထက်ပိုက မျှော်လင့်ထားသော အပြုအမူများမှာ စွမ်းရည်ဖော်ပြချက်၊ အကြံပြု prompt၊ ရပ်တန့်ခလုတ်ပါသော streaming၊ ကိုးကားချက် သို့မဟုတ် ရင်းမြစ်စာရင်း၊ ပြန်ပြင်ရခက်သော လုပ်ရပ်မတိုင်မီ အတည်ပြုချက်၊ ပြန်ပြင်နိုင်သော အထွက်အတွက် undo၊ loading နှင့် error အခြေအနေဖြစ်သည်။ NN/g ၏ ၂၀၂၆ ဧပြီ ၂၄ လမ်းညွှန်က နိဒါန်းတွင် ခေါင်းစဉ်နှင့် ခလုတ်အဖြစ် အကြံပြု prompt၊ စာမျက်နှာများအနှံ့ ရောက်နိုင်မှု၊ အဖြေအဆုံးသို့ autoscroll မလုပ်ရန် ပါသည် ([10 Guidelines](https://www.nngroup.com/articles/ai-chatbots-design-guidelines/))။ Cloudscape က `[1]`၊ `[2]`၊ `[3]`၊ popover၊ Sources ခေါင်းစဉ်ကို သတ်မှတ်သည်။ Carbon က AI label နှင့် explainability popover ဖြင့် “AI သုံးနေသည်” ကို ပြသည်။ Spectrum က tool call ကို `ExecutionTrace` ထဲတွင် ခေါက်နိုင်သော မှတ်တမ်းအဖြစ် ထားသည်။

မဆုံသေးသော အရာကို စနစ်စည်းအဖြစ် မသွင်းပါ။ Chat သည် အခွံလော၊ အလုပ် UI ထဲက component တစ်ခုလောကို NN/g၊ Smashing၊ Kamushken က တစ်မျိုး၊ Cloudscape၊ Carbon AI Chat၊ Spectrum က chat ကို ပထမတန်းပုံစံအဖြစ် ဆက်ထုတ်သည်။ ယုံကြည်မှုရာခိုင်နှုန်းကို Victor Yocco က ၂၀၂၆ ဖေဖော်ဝါရီ ၁၁ Smashing ဆောင်းပါးတွင် ဥပမာပေးပြီး၊ Roman Kamushken က ၂၀၂၆ စက်တင်ဘာ ၂၁ တွင် Verified၊ Assumed၊ Could not do ဟူသော အောက်ခြေစာကြောင်းဖြင့် အစားထိုးသည်။ Microsoft ၏ ၂၀၂၅ ဧပြီ ၁၁ Agent UX စည်းမျဉ်းက သေချာမှုအဆင့်ကို မြင်နိုင်ရန် တောင်းပြီး ဂဏန်းကို မသတ်မှတ်ပါ ([UX design for agents](https://microsoft.design/articles/ux-design-for-agents/))။ ကိုးကားချက် လိုအပ်မှုသည် တည်ငြိမ်ပြီး၊ widget ပုံစံသည် မတည်ငြိမ်ပါ။ Cloudscape ၏ inline နံပါတ်နှင့် Nancy Niu က Salesforce စကေးတွင် inline ကိုးကားချက်က ဖတ်စီးမှုကို ချိုးသောကြောင့် popover သို့မဟုတ် panel သို့ ရွှေ့သည်ဟု ရေးချက်သည် ပုံစံမတူပါ။ အဆင့်တိုင်းတွင် အတည်ပြုချက်တောင်းခြင်းကို Kamushken က approval fatigue အဖြစ် ၂၀၂၆ တွင် တင်ပို့နေသော ဆန့်ကျင်ပုံစံဟု ခေါ်သည်။ Memory editor၊ multi-agent handoff၊ ရာခိုင်နှုန်း confidence အတွက် အမည်ပေး component ကို ဤရှာဖွေမှုထဲက ဒီဇိုင်းစနစ်စာမျက်နှာတစ်ခုကမျှ မသတ်မှတ်ပါ။ Microsoft က ၂၀၂၅ ဧပြီတွင် memory စနစ်များ ဖွံ့ဖြိုးဆဲဖြစ်ပြီး စည်းမျဉ်းများသည် ရှေ့ကို မျှော်ကြောင်း ရေးသည်။

Accessibility တွင်လည်း ချက်ပြုတ်နည်းတစ်ခုတည်း မရှိပါ။ a11ypatterns က ၂၀၂၅ ဇူလိုင် ၂၉ တွင် streaming စာကို live region ထဲ မထားရန်၊ `aria-busy` ထားရန်၊ စတင်ခြင်းနှင့် ပြီးခြင်းကို သီးခြား polite status ဖြင့် ကြေညာရန် ရေးပြီး၊ ဤနည်းသည် စဉ်းစားထားသော နည်းလမ်းဖြစ်ကာ တည်ငြိမ်စံမဟုတ်သေးကြောင်း ဝန်ခံသည်။ WCAG 2.2 SC 4.1.3 နှင့် ချိတ်သည် ([When AI Never Stops Talking](https://a11ypatterns.org/index.php?r=%2Fpatterns%2Fai-streaming-response))။ Cloudscape ၏ ၂၀၂၄ နိုဝင်ဘာစာမျက်နှာက မက်ဆေ့အသစ်ကို ဖုံးကွယ်ထားသော live region ဖြင့် ကြေညာရန် ရေးသည်။ streaming အတွက် သီးခြား W3C မှတ်စုကို ဤရှာဖွေမှုက မတွေ့ပါ။ အရောင်တစ်ခုတည်း၊ sparkle၊ ရာခိုင်နှုန်းတို့သည် accessibility ရင်းမြစ်များ၏ ဝေဖန်ချက်ကို မဖြတ်ပါ။ ရိုးရိုး component စာကြည့်တိုက်နှင့် ကွာသော အပိုလိုအပ်ချက်မှာ အချိန်နှင့် အသိပညာဘက်ဖြစ်သည်။ UI သည် အသုံးပြုသူ မလုပ်ဘဲ ပြောင်းသည်၊ အကြောင်းအရာ မှားနိုင်သည်၊ အခြားစနစ်ပေါ် လုပ်ဆောင်နိုင်သည်။ ထို့ကြောင့် အခြေအနေကြေညာမှု၊ focus ကို composer တွင် ထားမှု၊ ကိုးကားချက်နှင့် မသေချာမှုကို စာသားဖြင့် ထားမှု၊ ပြောသူကို စနစ်ဟု တံဆိပ်ကပ်မှု၊ stop၊ undo၊ ဘာပြောင်းသွားသည် မှတ်တမ်းတို့သည် ခလုတ်စာကြည့်တိုက်၏ ဆန့်ကျင်ဘက်၊ အရောင်စည်းနှင့် ခလုတ်ဘုတ်အသုံးပြုခွင့်အပြင် ထပ်တိုးအလုပ်ဖြစ်သည်။

အသံနေအသံထားကိုလည်း မျှဝေစံအဖြစ် မကူးပါ။ Cloudscape က “please”၊ “thank you”၊ အာမေဍိတ်၊ “e.g.” ကို တားပြီး စနစ်ကို “generative AI assistant”၊ အဖြေကို “responses” ဟု ခေါ်သည်။ Salesforce က ကြိုဆိုစာ၊ ထုတ်ဖော်ချက်၊ ဥပမာမေးခွန်း၊ နယ်ပယ်၊ တုံ့ပြန်ချက် သို့မဟုတ် လူဆီပို့လမ်းကို agent တိုင်းတွင် ထားရန်နှင့် “I may make mistakes, so review my responses for accuracy.” ဝါကျကို တောင်းသည်။ နှစ်ခုစလုံး ထုတ်ပြန်ထားသော ဗီဇများဖြစ်ပြီး ဆန့်ကျင်ဘက်ဖြစ်သည်။ အသေးစားအဖွဲ့သည် ကိုယ့်အမှတ်တံဆိပ်၏ ဝါကျကို ရေးမည်ဆိုလျှင်၊ ဤနှစ်ခုအနက် ဘယ်စာမျက်နှာကို လိုက်မည်ကို ကိုယ့်ဘာသာ ရွေးရမည်။ မှတ်စုများက တစ်ခုကို အနိုင်မပေးပါ။

## နိဂုံး

၂၀၂၆ နိုဝင်ဘာ၏ ကွင်းဆင်းပုံမှာ agent ကို စာဖတ်သူအသစ်ဖြစ်အောင် ပိုက်ခင်းခြင်းက၊ ထိုစနစ်ကို ကျရှုံးအောင် လုပ်နိုင်ခြင်းထက် ပိုမြန်နေသည်။ အများပြည်သူဇယားတွင် token နှင့် API ရှိပြီး၊ ထုတ်ကုန်အဖွဲ့က ဖတ်ရမည့် ညွှန်ကြားချက် မရှိပါ။ အဓိပ္ပာယ်ဖွင့်ဆောင်းပါးများက ပိုက်တစ်ခုတည်း မလုံလောက်ကြောင်း သဘောတူပြီး၊ “agentic” ဆိုသည်မှာ ပြင်ပ agent က ဖတ်နိုင်ခြင်းလော၊ စနစ်ကိုယ်တိုင်က ရွေးချယ်စစ်ဆေးခြင်းလောတွင် ကွဲနေသည်။ အသေးစားအဖွဲ့တစ်ဖွဲ့ ဤရင်းမြစ်များ၏ ထပ်နေသောအပိုင်းကို လိုက်သောအခါ ရလဒ်မှာ ကိုယ်တိုင်ကျန်းမာသော စနစ်မဟုတ်ပါ။ ဘယ်အဓိပ္ပာယ်ကို တည်ဆောက်နေသလဲ စာရွက်ပေါ် ရောက်ပြီး၊ မော်ဒယ်အပြင်ဘက်တွင် ကျရှုံးနိုင်သော စည်းရှိပြီး၊ ရေးခွင့်သည် လူတစ်ဦး၏ ခွင့်ပြုချက်နောက်တွင် ရှိသော catalog ဖြစ်သည်။

Aestheria က ၂၀၂၆ ဩဂုတ်တွင် မဖြေရှင်းရသေးဟု မှတ်ထားသော အကွက်သုံးကွက်၊ လုပ်ဆောင်နေစဉ် ရှင်းပြချက်၊ ထုတ်ထားသော ထုတ်ကုန်က ဘာနှင့် စစ်သလဲ၊ မှားလျှင် ကုစားလမ်း၊ သည် ဤအစီအစဉ်၏ နယ်နိမိတ်အတိုင်း ကျန်သည်။ နောက်အဆင့်များသည် စစ်နိုင်သော catalog နှင့် ပြန်ကြည့်နိုင်သော ပြောင်းလဲမှုသို့ ပို့သည်။ Indeed၊ Primer၊ Spotify တို့၏ လည်ပတ်ပုံအသေးစိတ်သည် ပိုင်ရှင်အဖွဲ့၏ RFC ထဲတွင် မရှိသေးဘဲ ညီလာခံပြန်ပြောချက်ထဲတွင် ရှိနေသေးသောကြောင့်၊ အသေးစားအဖွဲ့အတွက် ကူးရမည့် ဂဏန်းပစ်မှတ်မဟုတ်ပါ။ ကူးရမည့် အစီအစဉ်သည် အခြေအနေပါသော အစီအစဉ်ဖြစ်သည်။ စနစ်က စာပိုဒ်နှင့် ပြားသော အရောင်ဖြစ်နေလျှင် မျိုးစေ့။ စာချုပ်ရှိပြီးသားဖြစ်လျှင် ဖိုင်နှစ်ဖိုင်နှင့် ဖတ်ခွင့်သီးသန့် server။ Chat၊ ရာခိုင်နှုန်း၊ handoff တို့ကို ထိုအစီအစဉ်ထဲသို့ ထည့်လျှင် ရလဒ်သည် Carbon နှင့် Spectrum စတင်ထုပ်ထားသော ထုတ်ကုန်မျက်နှာပြင် kit ဖြစ်ပြီး၊ စနစ်ကို စစ်နိုင်အောင် လုပ်ခြင်း မဖြစ်သေးပါ။
